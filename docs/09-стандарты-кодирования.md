# Стандарты кодирования CPM v3

Свод требований к коду, выведенных из документации ядра. Обязательны для всех агентов, работающих над проектом.

## Пространства имён

- Все классы — в базовом пространстве имён `\CPM\v3\`.
- Ядро — `\CPM\v3\Core\`. Модули — свои подпространства (см. `docs/01-классы.md`).

## Загрузка классов

- **Запрещён автозагрузчик** (Composer и т.п.). Классы загружаются менеджерами модулей через `require()`.
- Ядро грузится всегда; классы UI — только при рендере интерфейса; классы REST — при обработке REST-запросов.

## Хранение данных

- Все данные — только штатными средствами WordPress: Custom Post Type + `postmeta`.
- Собственные таблицы БД не создаются (исключение — легаси-таблица `in_cpm_user_role`, только чтение для обратной совместимости).
- Запись участников всегда только в мета-поле `_team` нового формата.

## SQL-запросы

- Все SQL в спецификациях — **прототипы** (таблицы `in_posts`, `in_postmeta`, `in_cpm_user_role`).
- В продакшн-коде:
  - только параметризованные запросы `$wpdb->prepare()` — значения фильтров никогда не подставляются конкатенацией;
  - имена таблиц только через `$wpdb->posts`, `$wpdb->postmeta`, `$wpdb->comments`, `$wpdb->commentmeta`;
  - фильтр по пользователю формируется динамически: параметр `is_admin` (`true` для администратора WordPress — тогда фильтр по участнику не применяется), для остальных — `team LIKE ...` с ID текущего пользователя через `$wpdb->prepare()`.

## Единые имена (обязательно, в истории были расхождения)

- Метод подготовки аргументов для сохранения: **`get_wp_args()`** (не `get_args()`).
- Фабричный метод выборки сущностей: **`load_list()`** (не `get_list()`).
- Константа Custom Post Type: **`CPT`** (не `CTP`).

## Логирование

- Везде только через `\CPM\v3\Plugin::get_instance()->log( $message, $level )`.
- Уровни: `error`, `warn`, `info`, `debug`. `debug` — удаляется из кода перед релизом.

## Права доступа

- Роль пользователя определяется `ACL::get_role( $entity )`.
- Ограничения прав реализуются декораторами (`can_modify()`); ядро выбрасывает `AccessDeniedException` при запрете операции (не «молчаливый no-op»).
- Удаление проекта — только для `ADMINISTRATOR` (проверка в `delete()` проекта, а не в декораторе).

## Комментарии к коду

- Не добавлять лишних комментариев. Комментарии уместны там, где реализация нетривиальна (например, SQL-запросы обратной совместимости).

## Проверка перед сдачей

- Код должен соответствовать стандартам кодирования WordPress (PHPCS) при доступности инструмента.
- Проверка типов/синтаксиса PHP (`php -l`) перед коммитом.
