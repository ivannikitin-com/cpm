# CPM v3 — WordPress-плагин управления проектами (аналог Basecamp)

CPM v3 (Customer Project Manager v3) — плагин WordPress для отслеживания задач в проектах клиентов. Модульная система: ядро, REST API, UI, расширения.

Этот каталог `docs/` — **единая точка входа в спецификации для агентской разработки**. Все спецификации являются переносом/дистилляцией заметок Obsidian (`C:\Users\ivang\PKM\Работа\ivannikitin.com\CPM\CPM v3`), оформленных в виде, пригодном для разработки без доступа к Obsidian.

## Как пользоваться этой документацией

1. Начните с этого файла: архитектура и ключевые принципы.
2. `01-классы.md` — полный список классов, пространства имён и пути файлов.
3. Для работы над ядром переходите в `docs/core/README.md` — там карта ядра и всех его классов.
4. Для работы над модулем REST API / UI / расширений — соответствующие файлы в `docs/`.
5. Открытые вопросы, требующие решения, собраны в `docs/core/открытые-вопросы.md`.

## Архитектура системы

CPM v3 построена по модульному принципу и состоит из модулей:

| Модуль | Назначение | Спецификация |
| ------ | ---------- | ------------ |
| **Ядро (Core)** | Классы сущностей данных, хранение в БД WordPress, права доступа | `docs/core/` |
| **REST API** | Контроллеры сущностей для интеграции с внешними сервисами и UI | `docs/06-модуль-rest-api.md` |
| **UI** | Внешний визуальный интерфейс на сайте WordPress | `docs/07-модуль-ui.md` |
| **Расширения (Extensions)** | Единый механизм загрузки и управления расширениями | `docs/08-модуль-расширения.md` |

Инициализацию всей системы и её модулей выполняет класс `Plugin` (`docs/02-plugin.md`).

## Ключевые принципы (обязательные)

1. **Хранение данных только штатными средствами WordPress.** Все данные CPM v3 хранятся в Custom Post Type и мета-данных записей (`postmeta`). Создание собственных таблиц БД запрещено, кроме явно оговорённых случаев (легаси-таблица `in_cpm_user_role` используется только для чтения старой версии).
2. **Бесшовный переход со старой версии без скрипта миграции.** Классы читают данные и старого, и нового формата (приоритет нового через `COALESCE()`), а сохраняют всегда только в новом формате. Подробнее: `docs/core/совместимость.md`.
3. **Производительность выборок.** Списки сущностей выбираются **одним параметризованным SQL-запросом** на тип сущности (SQL хранится в статическом свойстве `SQL` класса сущности), а не через `WP_Query`. Предыдущая версия делала 400–500 запросов на инициализацию — это недопустимо.
4. **Нет автозагрузчика.** Классы загружаются менеджерами модулей через `require()`, чтобы экономить память (ядро грузится всегда, UI — только при рендере интерфейса).
5. **Права на уровне проекта.** Роль пользователя определяется командой `Team` проекта. Права на сущность проверяются декораторами, оборачивающими сущность.
6. **Ядро не занимается отображением.** Парсинг Markdown/шорткодов, рендер картинок/иконок — зона ответственности UI.

## Ключевые требования к коду

- Базовое пространство имён: `\CPM\v3\`. Ядро: `\CPM\v3\Core\`.
- Все пути в документации вида `CPM_PLUGIN_DIR/...` — это путь к папке плагина.
- SQL-запросы в спецификациях — **прототипы** (таблицы `in_`). В продакшн-коде — параметризованные запросы `$wpdb->prepare()` и имена таблиц `$wpdb->posts`, `$wpdb->postmeta`.
- Логирование централизованное: `\CPM\v3\Plugin::get_instance()->log($msg, $level)`.
- Подробнее: `docs/09-стандарты-кодирования.md`.

## Разработка на стенде

Разработка ведётся на стенде в Docker (WordPress). `docker-compose` будет добавлен отдельно. В проекте присутствует сервисная папка `sql/` с SQL-скриптами для отладки (в коде плагина не используется).
