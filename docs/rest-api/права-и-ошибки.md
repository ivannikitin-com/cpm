# Права и ошибки в REST API CPM v3

Как REST API соблюдает права доступа CPM и как переводит исключения ядра и ошибки валидации в HTTP-ответы.

## Принцип: права проверяет только ядро

Контроллеры REST API **не проверяют права самостоятельно**:

- Сущности приходят из `Core_Manager::load_list()`, который уже ограничивает выборку по текущему пользователю (фильтр `is_admin OR team LIKE ...` в SQL) и оборачивает каждый объект декоратором по таблице прав (`docs/core/core-manager.md`, `docs/core/права-и-роли.md`).
- Операции изменения (`save()`, `delete()`, запись свойств через `__set`) идут через декоратор: при запрете он выбрасывает `AccessDeniedException` (`docs/core/base-decorator.md`).

Задача слоя REST — только перехватить результат и вернуть корректный HTTP-код.

## Аутентификация и базовая авторизация

Перед правами CPM WordPress проверяет саму аутентификацию (кто пользователь) — см. `аутентификация.md`. Контроллеры дополнительно используют `permission_callback`:

- список/одна сущность: требуется аутентифицированный пользователь (`is_user_logged_in()`); какие именно сущности вернутся — решает ядро;
- создание/обновление/удаление: аналогично — аутентифицированный пользователь, а конкретное право определяет декоратор ядра.

Такой подход не дублирует таблицу прав в двух местах и исключает расхождение «контроллер разрешил, ядро запретило» и наоборот.

> **Почему не `current_user_can()` по возможностям WP**: права CPM не сводятся к возможностям WordPress — они определяются командой проекта (`_team`) и таблицей прав (`docs/core/права-и-роли.md`). Единственный источник прав — `ACL` + декораторы ядра.

## Маппинг исключений ядра в HTTP-ответы

Единая точка перехвата — `Base_Controller` (`архитектура.md`). Иерархия исключений — `docs/core/ошибки.md`.

| Исключение ядра | HTTP-код | `WP_Error` code | Когда возникает |
| --------------- | -------- | --------------- | --------------- |
| `AccessDeniedException` | `403 Forbidden` | `cpm_forbidden` | Запрещена модификация (декоратор `can_modify()` = false), запрещено создание типа |
| Не найдено (пустой результат `load_list()`) | `404 Not Found` | `cpm_not_found` | Сущность отсутствует **или** недоступна пользователю (нет прав / `no_access`) |
| `EntitySaveException` | `500 Internal Server Error` | `cpm_save_failed` | Ошибка сохранения/удаления в БД |
| `BadUserException` | `404`/`400` | `cpm_user_not_found` | Пользователь не найден при загрузке |
| Валидация аргументов запроса | `400 Bad Request` | `cpm_invalid_param` / штатные `rest_invalid_param` | Неверный тип/значение параметра |

Особенности:

- **Доступ к чужой/запрещённой сущности выглядит как `404`, а не `403`.** Сущность, на которую у пользователя нет прав, ядро не возвращает в `load_list()` (для `no_access` — исключает, для остальных — фильтрует по проекту). Для клиента это неотличимо от «не существует» — так не раскрывается факт существования сущности.
- **`403`** контроллер возвращает только там, где сущность доступна для чтения, но запрещена модификация (например, `DELETE /cpm/v1/task_list/{id}` для роли без права изменять списки, `POST /cpm/v1/activity` — создание журнала).

### Формат ответа об ошибке

Стандартный формат WordPress REST:

```json
{
  "code": "cpm_forbidden",
  "message": "У вас нет прав на это действие",
  "data": { "status": 403 }
}
```

Сообщения — человекочитаемые, на русском (как остальной UI плагина). Точные тексты фиксируются при реализации (`открытые-вопросы.md`).

## Поведение по операциям

### Список (`GET /{type}`)

1. Собрать аргументы из query-параметров (допустимые фильтры — `маршруты.md`).
2. Прогнать валидацию параметров (см. ниже); при ошибке — `400`.
3. `Core_Manager::get_instance()->load_list( $type, $args )`.
4. Сериализовать каждый объект; вернуть массив (возможно, с заголовками пагинации — см. `маршруты.md`).

Недоступные пользователю сущности просто отсутствуют в ответе — это штатное поведение, не ошибка.

### Одна сущность (`GET /{type}/{id}`)

1. `load_list( $type, array( 'id' => (int) $id ) )`.
2. Пустой массив → `404 cpm_not_found` (в т.ч. сущность существует, но недоступна).
3. Иначе сериализовать `$list[0]`.

### Создание (`POST /{type}`)

1. Валидация тела (обязательные поля типа: `parent`/`project_id` для дочерних, `title` и т.п.).
2. `Core_Manager::get_instance()->create( $type, $args )`.
3. При `AccessDeniedException` → `403` (или `404`, если проверка прав внутри ядра трактует иначе).
4. Успех → `201 Created` с объектом сущности.

### Обновление (`POST /{type}/{id}`)

1. `load_list( $type, array( 'id' => $id ) )` → пусто = `404`.
2. Применить к объекту только поля, разрешённые к записи (см. `схемы.md`). Запись идёт через декоратор (`__set`), который при запрете бросит `AccessDeniedException` → `403`.
3. `$entity->save()`.
4. Успех → `200 OK` с обновлённым объектом.

### Удаление (`DELETE /{type}/{id}`)

1. `load_list( $type, array( 'id' => $id ) )` → пусто = `404`.
2. `$entity->delete()` (декоратор проверит права; `AccessDeniedException` → `403`).
3. Успех → `204 No Content` (решение №23).

### Экшены (`POST /{type}/{id}/archive`, `/team`, `/thumbnail` и т.п.)

1. Валидация тела экшена (своя схема для каждого экшена).
2. Загрузить сущность (`load_list`) → пусто = `404`.
3. Выполнить действие ядра (например, `archive()`, `set_coordinator()`). Права соблюдаются декоратором: `save()`/запись свойств через `__set` при запрете бросят `AccessDeniedException` → `403`.
4. Успех → `200 OK` с обновлённым объектом.

Полный список экшенов — `маршруты.md`.

## Валидация параметров

Используются штатные механизмы `register_rest_route()`:

- `args[].validate_callback` — проверка типа/диапазона;
- `args[].sanitize_callback` — приведение (например, `absint()` для ID);
- `args[].required` — обязательные поля (например, `parent` при создании задачи);
- авто-схема (`get_item_schema()`) для тела — типы полей из `схемы.md`.

**Решение по телу запроса** (create/update): неизвестные поля и поля, доступные только на чтение, → `400 Bad Request` (`cpm_invalid_param` / штатные `rest_invalid_param`). Read-only поля изменяются только через маршруты-экшены (`маршруты.md`), где тело экшена валидируется отдельно.

**Сообщения об ошибках** — человекочитаемые, внятные тексты на русском языке (решение №19). Стандартные ошибки валидации WordPress остаются как есть (`rest_invalid_param` и т.п.); финальные тексты фиксируются в контроллерах при реализации.

## Логирование

Неожиданные ошибки (`EntitySaveException`, прочие исключения вне иерархии CPM) логируются через `\CPM\v3\Plugin::get_instance()->log( $message, 'error' )` перед возвратом `500`. Ошибки прав (`AccessDeniedException`) не логируются как сбои — это штатный отказ доступа (`docs/core/ошибки.md`).
