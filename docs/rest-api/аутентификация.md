# Аутентификация и авторизация в REST API CPM v3

Как REST API CPM v3 определяет пользователя и каким образом применяются права CPM.

## Два уровня контроля

| Уровень | Что проверяет | Механизм |
| ------- | ------------- | -------- |
| Аутентификация | «Кто пользователь?» | Стандартная аутентификация WordPress REST API (cookie, application passwords) |
| Права CPM | «Что ему можно в проекте?» | Ядро: `ACL` + декораторы (см. `права-и-ошибки.md`) |

Аутентификацию модуль REST API **не изобретает**: используются штатные механизмы WordPress REST. После того как WordPress определил текущего пользователя, все проверки прав CPM выполняет ядро по `get_current_user_id()`.

## Способы аутентификации

### 1. Cookie-аутентификация (для UI и встроенных страниц)

Стандартный механизм WordPress: пользователь залогинен на сайте, запросы идут с куки WordPress. Для REST-запросов WordPress требует заголовок `X-WP-Nonce` с nonce:

```
X-WP-Nonce: <wp_rest_nonce>
```

Nonce создаётся через `wp_create_nonce( 'wp_rest' )`. Это основной способ для React UI: приложение работает в контексте сайта WordPress (куки доступны), nonce передаётся в каждом запросе.

### 2. Application Passwords (для внешних сервисов и интеграций)

Штатная возможность WordPress 5.6+ — пароли приложений:

```
Authorization: Basic base64(login:application_password)
```

Применяется для внешних сервисов, которые интегрируются с CPM (синхронизация, импорт/экспорт, боты). Никакой дополнительной логики в модуле не требуется — WordPress сам аутентифицирует пользователя.

> Другие способы (JWT-плагины, собственные ключи API) **не используются** — в приоритете штатные механизмы WordPress (`docs/09-стандарты-кодирования.md`: всё только штатными средствами).
>
> **Решение (№24, `открытые-вопросы.md`)**: собственный API-ключ для внешних сервисов **не вводится**. Аутентификацию выполняет штатный WordPress, авторизацию — контроллер (через ACL/декораторы ядра). «Ключ» внешнего сервиса — это **пароль приложения**, который создаётся штатными средствами WordPress (профиль пользователя → Application Passwords) и используется как `Authorization: Basic`. Никакой дополнительной логики в модуле для этого нет.

## Публичные vs защищённые маршруты

Все маршруты CPM v3 защищены: неаутентифицированный пользователь получает `401`/`403` от штатного слоя WordPress. Публичных (открытых) маршрутов нет — данные CPM приватные.

| Ситуация | Результат |
| -------- | --------- |
| Нет аутентификации | `rest_cookie_invalid_nonce` / `401`, у внешнего клиента без учётки — `401` |
| Есть аутентификация, прав CPM нет | сущность не возвращается/`404`, модификация — `403` (см. `права-и-ошибки.md`) |

## Nonce для контроллеров

`permission_callback` у маршрутов проверяет `is_user_logged_in()` — а конкретную nonce-проверку WordPress выполняет автоматически для cookie-запросов. Контроллерам CPM не нужно реализовывать собственную nonce-логику.

> Примечание по безопасности: даже если `permission_callback` пропустит запрос, сущности всё равно отфильтрует ядро (защита в глубину — см. `docs/core/ошибки.md`, п. «Ошибка прав как граница безопасности»).

## Пользователь в ответах API

Сущности в ответах содержат только ID автора (`author`). Данные пользователей (имя, аватар) в списках **не подгружаются**, чтобы избежать N+1-запросов (`схемы.md`). Отдельный эндпоинт пользователей **не создаётся** (решение №13): там, где возможно, используется штатный WP REST. Вопрос имён/аватаров участников проекта для UI остаётся открытым на уровне ядра/UI — см. `открытые-вопросы.md`.
