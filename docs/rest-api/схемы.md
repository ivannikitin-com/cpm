# Схемы запросов и ответов REST API CPM v3

Единый словарь полей для JSON. Имена полей **совпадают со свойствами сущностей ядра** (snake_case), чтобы не вести два словаря «свойство ядра ↔ поле API». Сериализация выполняется в `prepare_item_for_response()` (`архитектура.md`).

## Общие правила

- Поле включается в ответ, только если у него есть значение (кроме `id`, который всегда присутствует).
- **Контент** (`content`) отдаётся как хранится (Markdown / HTML / шорткоды). Парсинг — зона UI (`docs/core/контент-сущностей.md`).
- **Даты** отдаются в формате хранения ядра (`Y-m-d H:i:s`, например `2019-11-18 00:00:00`) — **решение**: конвертация в ISO 8601 не выполняется (`открытые-вопросы.md`, №16).
- **Команда (`team`)** сериализуется как объект-карта `{ "user_id": "role", ... }` (`{"12":"manager","15":"client"}`) — ровно формат хранения. Полные данные пользователей (имя, аватар) этим способом **не подгружаются**, чтобы избежать N+1-запросов при списках. Отдельный REST-эндпоинт пользователей **не создаётся** (решение №13); вопрос данных пользователей для UI остаётся на уровне ядра/UI (`открытые-вопросы.md`).
- **Вложенные данные проекта** у сущностей `Project_Entity` отдаются плоскими полями `project_id`, `project_title`, `project_slug` (как свойства ядра), а не вложенным объектом.
- **Поля-экшены**: `team`, `active`, `thumbnail_id` и др. — **не записываются** через общий `POST /{type}/{id}` (попытка записи → `400`). Для них есть отдельные маршруты-экшены (`маршруты.md`). Исключение — поля, которые допустимо указать сразу при создании (`POST /{type}`), например `coordinator` у проекта: дальше оно меняется только экшеном.
- **Неизвестные поля** в теле запроса (create/update) → `400 Bad Request`.

## Общие поля Entity

Общие для всех сущностей на CPT (`docs/core/entity.md`, `docs/core/мета-поля.md`):

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `id` | int | — (read) | ID сущности |
| `parent` | int | create | ID родительской сущности |
| `author` | int | — (read) | ID автора; при создании определяется текущим пользователем |
| `title` | string | create/update | Заголовок |
| `content` | string | create/update | Содержимое (Markdown и др.) |
| `created_at` | string | — (read) | Дата создания |
| `slug` | string | create/update | Слаг; пустой → генерируется WordPress |
| `menu_order` | int | create/update | Позиция сортировки |
| `thumbnail_id` | int | — (read) | ID вложения-картинки (featured image), `0` = нет; устанавливается экшеном `/{type}/{id}/thumbnail` |
| `team` | object | — (read) | Участники `{user_id: role}`; изменяется экшеном `/{type}/{id}/team` |

## Поля сущностей проекта (`Project_Entity`)

Для всех дочерних сущностей проекта добавляются (read; при create вычисляются ядром из `parent`):

| Поле | Тип | Назначение |
| ---- | --- | ---------- |
| `project_id` | int | ID проекта |
| `project_title` | string | Название проекта (денормализация) |
| `project_slug` | string | Слаг проекта |

## Схемы по сущностям

### project

Источник: `docs/core/project.md`. Наследует общие поля `Entity`.

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `coordinator` | int | create | Координатор (Product Owner), ID пользователя; при создании можно указать сразу |
| `active` | string | — (read) | `yes` — активный, `no` — архивный |

`active` и изменение `coordinator` после создания выполняются **экшенами**, а не через общий update: `POST /cpm/v1/project/{id}/coordinator`, `POST /cpm/v1/project/{id}/archive`, `POST /cpm/v1/project/{id}/unarchive` (см. `маршруты.md`). В теле общего `POST /cpm/v1/project/{id}` поля `active` и `coordinator` не принимаются (`400`).

Пример ответа `GET /cpm/v1/project/123`:

```json
{
  "id": 123,
  "parent": 0,
  "author": 1,
  "title": "Сайт клиента",
  "content": "Описание проекта",
  "created_at": "2019-11-18 00:00:00",
  "slug": "client-site",
  "menu_order": 1,
  "thumbnail_id": 0,
  "team": { "12": "manager", "15": "client" },
  "coordinator": 12,
  "active": "yes"
}
```

### task_list

Источник: `docs/core/task-list.md`. Наследует `Entity` + `Project_Entity`.

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `project_id`, `project_title`, `project_slug` | — | — (read) | Проект |
| `milestone` | int | create/update | ID вехи; `-1` = веха не назначена |
| `team` | object | — (read) | Дефолтовые участники задач списка; изменяется экшеном `/{type}/{id}/team` |

`parent` списка задач = ID проекта.

### task

Источник: `docs/core/task.md`. Наследует `Entity` + `Project_Entity`.

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `task_list_id` | int | — (read) | ID списка задач (производное от `parent`) |
| `task_list_title` | string | — (read) | Название списка |
| `task_list_slug` | string | — (read) | Слаг списка |
| `start` | string | create/update | Дата/время старта |
| `due` | string | create/update | Срок |
| `completed` | int | create/update | `1`/`0` — завершена ли |
| `completed_on` | string | — (read) | Дата завершения (выставляется ядром) |
| `completed_by` | int | — (read) | Кто завершил (выставляется ядром) |
| `task_privacy` | string | create/update | `yes`/`no` — только для сотрудников |
| `team` | object | — (read) | Исполнители (ответственные); изменяется экшеном `/{type}/{id}/team` |

При создании задачи `parent` = ID списка задач. Флаг `completed` принимает `1`/`0`; поля `completed_on`/`completed_by` заполняются ядром при переходе в завершённое состояние.

### message

Источник: `docs/core/message.md`. Наследует `Entity` + `Project_Entity`.

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `message_privacy` | string | create/update | `yes`/`no` — приватность («только для сотрудников») |
| `milestone` | int | create/update | ID вехи; `0` = веха не назначена |
| `files` | array<int> | — (read) | ID вложений обсуждения |

`parent` сообщения = ID проекта.

### milestone

Источник: `docs/core/milestone.md`. Наследует `Entity` + `Project_Entity`.

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `due` | string | create/update | Срок вехи |
| `completed` | int | create/update | `1`/`0` — завершена ли |
| `team` | object | — (read) | Дефолтовые участники задач списков вехи; изменяется экшеном `/{type}/{id}/team` |

### note

Источник: `docs/core/note.md`. Наследует `Entity` + `Project_Entity`. CPT — `cpm_docs` (не `note`).

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `doc_type` | string | create/update | `_custom_doc` — заметка; `_google_doc` — ссылка на внешний документ |

`parent` заметки = ID проекта. Команда `team` отсутствует (доступ — по команде проекта).

### comment

Источник: `docs/core/comment.md`. Хранится в таблице `comments` WordPress. Наследует `Entity` (специфичная реализация `save()`/`delete_entity()`).

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `parent` | int | create | ID сущности, к которой относится комментарий |
| `content` | string | create/update | Текст комментария |
| `author` | int | — (read) | Автор |
| `created_at` | string | — (read) | Дата создания |

`project_id`/`project_title`/`project_slug` у комментария вычисляются через цепочку родительства (`get_project()`), если родитель принадлежит проекту.

### attachment

Источник: `docs/core/attachment.md`. Наследует `Project_Entity`. Права — `Stuff_Decorator` (CLIENT — `no_access`).

| Поле | Тип | Запись | Назначение |
| ---- | --- | ------ | ---------- |
| `title` | string | — (read) | Имя файла без расширения |
| `mime_type` | string | — (read) | MIME-тип (например, `application/pdf`) |
| `is_image` | bool | — (read) | Является ли картинкой |
| `width` / `height` | int | — (read) | Размеры (для изображений) |
| `size` | int | — (read) | Размер в байтах |
| `project_id` | int | — (read) | Проект вложения (из мета `_project`) |
| `parent` | int | create | Сущность, к которой прикреплён файл |
| `file_url` | string | — (read) | Относительный URL содержимого: `/wp-json/cpm/v1/attachment/{id}/file` |

Создание — только `multipart/form-data` (`загрузка-файлов.md`). JSON-поля при создании не принимаются.

### activity

Источник: `docs/core/activity.md`. Запись журнала, **только чтение**.

| Поле | Тип | Назначение |
| ---- | --- | ---------- |
| `id` | int | `comment_ID` |
| `content` | string | Человекочитаемый текст действия (обычный текст, без шорткодов у новых записей) |
| `author` | int | Пользователь, выполнивший действие |
| `created_at` | string | Дата/время |
| `parent` | int | Сущность, к которой относится действие |

## Валидация полей при записи

- `id`, `author`, `parent`, `project_id`, числовые флаги — `int`, приводится через `absint()`/`(int)`.
- `completed` — `1`/`0`; строки-статусы (`yes`/`no`) — по смыслу поля (в экшенах `archive`/`unarchive` значение статуса не передаётся — экшен сам определяет его).
- `content`, `title` — строки; проходят стандартную санитизацию `sanitize_textarea_field()`/`wp_kses_post()` по типу поля (см. `права-и-ошибки.md`).
- **Неизвестные поля** в теле запроса → `400 Bad Request` (решение №17, `открытые-вопросы.md`).
- **Поля, помеченные `— (read)`, при попытке записи** через общий create/update → `400 Bad Request` (решение №18). Запись таких полей возможна только через соответствующие экшены (см. `маршруты.md`).
