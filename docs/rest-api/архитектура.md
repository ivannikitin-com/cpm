# Архитектура модуля REST API

Модуль REST API — тонкий слой поверх ядра CPM v3. Он регистрирует REST-маршруты WordPress, принимает HTTP-запросы, вызывает фабрику ядра и возвращает JSON.

## Место в архитектуре

```
внешний сервис  ──┐
                  ├── HTTP (REST) ──► REST_API_Manager ──► контроллеры ──► Core_Manager ──► БД
React UI          │                        (register_routes)   (сериализация)   (load_list/create)
```

- Классы модуля — в пространстве имён `\CPM\v3\REST\`, файлы — `CPM_PLUGIN_DIR/classes/rest_api/`.
- Менеджер модуля создаётся в классе `Plugin` по хуку `init` (см. `docs/02-plugin.md`). На этом этапе регистрируются маршруты, а сами классы контроллеров подключаются лениво.
- Ядро (`Core_Manager`) — единственный способ получить или сохранить сущность. REST API **не работает с БД напрямую** и **не вызывает `WP_Query`** — только `Core_Manager::load_list()` / `create()` (см. `docs/core/core-manager.md`).

## Класс REST_API_Manager

Синглтон-менеджер модуля (по образцу `Core_Manager`), файл `CPM_PLUGIN_DIR/classes/rest_api/rest_api_manager.php`.

| Член | Тип | Назначение |
| ---- | --- | ---------- |
| `instance` | REST_API_Manager (static, private) | Экземпляр класса |
| `namespace` | string | Пространство имён маршрутов: `cpm/v1` |
| `get_instance()` | static : REST_API_Manager | Возврат экземпляра |
| `register()` | void | Вешает обработчик на `rest_api_init` |
| `register_routes()` | void | Подключает контроллеры и вызывает их `register_routes()` |
| `require_controller( $name )` | void | `require()` файла контроллера через `require_class()` из `Base_Manager` |

Конструктор менеджера выполняется по хуку `init` WordPress, поэтому:

- в конструкторе подключать файлы контроллеров **нельзя** — контроллеры нужны только при REST-запросе;
- в конструкторе вызывается `add_action( 'rest_api_init', array( $this, 'register_routes' ) )`.

### Регистрация маршрутов (`rest_api_init`)

Самый ранний момент, когда ядро гарантированно инициализировано — хук `init`. WordPress инициализирует REST API позже, хук `rest_api_init` срабатывает уже после `init`, поэтому в момент `register_routes()`:

- `Core_Manager` уже создан (Plugin создал его на `init`);
- `require()` контроллеров безопасен и выполняется только при REST-запросе (экономия памяти — см. `docs/03-base-manager.md`).

Псевдокод:

```php
class REST_API_Manager extends Base_Manager {

	public function register() {
		add_action( 'rest_api_init', array( $this, 'register_routes' ) );
	}

	public function register_routes() {
		$controllers = $this->get_controllers();
		foreach ( $controllers as $controller ) {
			$this->require_controller( $controller );
			$instance = new $controller();
			$instance->register_routes();
		}
	}
}
```

## Иерархия контроллеров

**Решение**: контроллеры наследуют штатный `WP_REST_Controller` (стандартные `register_routes()`, `get_item()`, `prepare_item_for_response()`, валидация и discovery-схема). Общая для CPM логика выносится в промежуточные абстрактные классы, которые сами наследуют `WP_REST_Controller`:

```
Base_Controller (abstract, extends WP_REST_Controller)
 ├── Entity_Controller (abstract)             — CRUD-логика для одной сущности ядра
 │    ├── Project_Controller                  — сущность project
 │    ├── Task_List_Controller                — сущность task_list
 │    ├── Task_Controller                     — сущность task
 │    ├── Message_Controller                  — сущность message
 │    ├── Milestone_Controller                — сущность milestone
 │    ├── Note_Controller                     — сущность note
 │    ├── Comment_Controller                  — сущность comment (таблица comments)
 │    ├── Activity_Controller                 — сущность activity (только чтение)
 │    └── Attachment_Controller               — сущность attachment + /file (бинарный)
 └── (специальные маршруты добавляются в контроллеры сущностей как экшены)
```

### Base_Controller (abstract, extends WP_REST_Controller)

Общая логика:

| Метод | Назначение |
| ----- | ---------- |
| `register_routes()` (abstract) | Регистрирует маршруты сущности через `register_rest_route()` |
| `get_core()` | Возвращает `Core_Manager::get_instance()` |
| `get_type()` (abstract) | Строковый тип сущности ядра (`project`, `task`, …) — ключ для `load_list()` |
| `prepare_item_for_response()` | Сериализует сущность (объект с декоратором) в массив/`WP_REST_Response` |
| `get_item_schema()` | JSON Schema сущности (поля, типы) — используется и для валидации, и для документации |
| `get_collection_params()` | Параметры списка (`context`, `page`, `per_page`, фильтры) |

Права не проверяются контроллером отдельно — сущности приходят из ядра уже ограниченными декоратором.

### Entity_Controller (abstract)

Типовой CRUD для сущности ядра. Реализует четыре маршрута (см. `маршруты.md`):

| Метод | Назначение |
| ----- | ---------- |
| `get_items()` | `load_list( $type, $args )` из параметров запроса → список |
| `get_item()` | `load_list( $type, array( 'id' => $id ) )` → один объект или 404 |
| `create_item()` | `Core_Manager::create( $type, $args )` → объект или ошибка прав |
| `update_item()` | Загрузка сущности, применение свойств из запроса, `save()` |
| `delete_item()` | Загрузка сущности и `delete()` |

### Контроллеры сущностей

Конкретные контроллеры минимальны: переопределяют `get_type()`, схему полей (`схемы.md`) и допустимые аргументы. Особые случаи:

- `Activity_Controller` — только чтение (активность доступна только для чтения, декоратор `ReadOnly_Decorator`).
- `Attachment_Controller` — дополнительный маршрут `/{id}/file` для скачивания бинарного файла (`загрузка-файлов.md`).
- `Comment_Controller` — сущность хранится в таблице `comments`, но через ядро читается/создаётся так же (`load_list('comment', ...)`).
- В контроллеры, где нужны действия ядра, добавляются **маршруты-экшены** (изменение `team`, `archive()`/`unarchive()`, `set_coordinator()`, `set_thumbnail()` и т.п.) — см. `маршруты.md`. Экшены не являются полями общего update.

## Использование фабрики ядра

REST API работает с сущностями только через `Core_Manager`. Контроллеры получают уже обёрнутые декоратором объекты, поэтому:

- чтение списка: `Core_Manager::get_instance()->load_list( $type, $args )` — всегда массив;
- чтение одной: `load_list( $type, array( 'id' => (int) $id ) )` — массив из 0/1 элемента;
- создание: `Core_Manager::get_instance()->create( $type, $args )` — объект (при отсутствии прав `AccessDeniedException`);
- обновление: получить сущность, записать свойства (через `__set` декоратора — он сам проверит `can_modify()`), затем `$entity->save()`;
- удаление: получить сущность и вызвать `$entity->delete()` (декоратор проверит права).

Все исключения ядра перехватываются в `Base_Controller` и превращаются в `WP_Error` с HTTP-кодом — см. `права-и-ошибки.md`.

## Наследование ответов от сущностей

Контроллеры не строят ответы вручную. Для каждой сущности есть схема (`схемы.md`), по которой `prepare_item_for_response()` превращает объект сущности в массив. Правила сериализации:

- имена полей ответа = свойства сущности ядра (snake_case);
- значения берутся напрямую из свойств сущности (уже обёрнутой декоратором — права соблюдены);
- контент отдаётся как хранится (парсинг Markdown/шорткодов — в UI);
- вложенные объекты (`project`, `team`) сериализуются как плоские вложенные массивы (см. `схемы.md`);
- бинарный файл вложения отдаётся отдельным маршрутом `/file` с заголовками `Content-Type`, а не полем JSON.
