# Загрузка и скачивание файлов (attachment) в REST API

Спецификация работы с файлами вложений: приватное хранение, multipart-загрузка, проверка прав и отдача бинарного файла.

## Общие принципы (из ядра)

- Файлы CPM хранятся в **приватной подпапке** `uploads/cpm/`, доступ по прямой ссылке блокируется конфигом сервера. Отдаются только через REST (`docs/core/attachment.md`).
- Старые вложения не мигрируются: они лежат в общей `uploads/` и отдаются через тот же REST-механизм (прокси читает путь из метаданных).
- Класс `Attachment` (ядро) отвечает за хранение и доступ. Механизм загрузки в v3 реализован в ядре: `Attachment::validate_upload()` (whitelist `cpm_allowed_mime_types`, лимит `cpm_max_upload_size`), `Attachment::create_from_upload()` (сохранение в `uploads/cpm/`, запись вложения, привязки `_project`/`_parent`/`commentmeta._files`). См. `docs/core/attachment.md`.
- Права: `Attachment` доступен только сотрудникам (`Stuff_Decorator`): `MANAGER`/`CO_WORKER` — `modify_own` (свои), `CLIENT` — `no_access`.

Настоящий документ фиксирует, как этот механизм **выглядит со стороны REST API** и какую часть работы берёт на себя слой REST.

## Загрузка файла

### Запрос

```
POST /wp-json/cpm/v1/attachment
Content-Type: multipart/form-data
```

Тело формы:

| Поле | Тип | Обязательно | Назначение |
| ---- | --- | ----------- | ---------- |
| `file` | file | да | Сам файл (бинарные данные) |
| `parent` | int | да | ID сущности, к которой прикрепляется файл (задача, комментарий, обсуждение и т.п.) |
| `project_id` | int | да* | ID проекта (для привязки `_project`); может вычисляться ядром из `parent` |

\* — точный набор полей привязки определяется при реализации механизма загрузки в ядре (`docs/core/attachment.md`).

### Обработка (предлагаемый порядок)

1. Контроллер вложения принимает multipart-запрос и вызывает механизм ядра: `Attachment::validate_upload()` → `Attachment::create_from_upload( $file, $project_id, $parent )`.
2. Валидация (ядро): тип файла по whitelist `cpm_allowed_mime_types` / допустимые расширения; максимальный размер `cpm_max_upload_size` (по умолчанию — как у WordPress); наличие файла и отсутствие ошибки загрузки.
3. Файл сохраняется в приватную подпапку `uploads/cpm/`, в БД создаётся запись `attachment` с мета `_project` (проект) и привязкой к родителю (`_parent`; если родитель — комментарий, ID добавляется в `commentmeta._files`).
4. Ответ — `201 Created` с JSON-объектом вложения (`схемы.md`).

### Ошибки загрузки

| Ситуация | HTTP |
| -------- | ---- |
| CLIENT / нет прав сотрудника | `404`/`403` (см. `права-и-ошибки.md`) |
| Файл не передан или повреждён | `400` |
| Недопустимый тип файла | `400` |
| Превышен размер | `400` |
| Ошибка сохранения файла/БД | `500` |

## Скачивание файла

### Содержимое

```
GET /wp-json/cpm/v1/attachment/{id}/file
```

Ответ — бинарные данные с заголовками:

- `Content-Type: <mime_type вложения>`
- `Content-Length`
- `Content-Disposition: inline` (по умолчанию) или `attachment; filename="..."` при `?download=1`
- кэш-контроль: приватный кэш (`Cache-Control: private`), т.к. файл защищён правами

### Миниатюра (для изображений)

```
GET /wp-json/cpm/v1/attachment/{id}/file?size=thumbnail
```

`size` — зарегистрированный размер WordPress (например, `thumbnail`, `medium`, `full`). Для не-изображений параметр игнорируется либо возвращается оригинал. Уточняется: см. `открытые-вопросы.md`.

### Проверка прав при отдаче

1. Контроллер получает вложение: `load_list( 'attachment', array( 'id' => (int) $id ) )`.
2. Пустой результат → `404` (вложения нет или CLIENT без доступа).
3. Загрузка физического файла: путь берётся из метаданных вложения (`_wp_attached_file`), неважно — из новой `uploads/cpm/` или старой `uploads/`.
4. Если файла нет на диске → `404`.
5. Отдать поток с заголовками.

> Файл не должен быть доступен по прямой ссылке — только через этот маршрут. Конфигурация блокировки `uploads/cpm/` (nginx/.htaccess) — вне кода плагина (`docs/core/attachment.md`).
