# Тестирование модуля REST API

Матрица покрытия и стратегия тестирования REST-слоя. Общие правила и два уровня тестов — в `tests/README.md`, конвенции — в `tests/стандарты-тестов.md`.

## Что тестируем

REST API — тонкий слой: регистрация маршрутов, сериализация сущностей в JSON, маппинг исключений ядра в HTTP-коды. Сами права и SQL уже покрыты тестами ядра (`tests/покрытие.md`) — их не дублируем.

| Область | Юнит [U] | Интеграция [I] |
| ------- | -------- | -------------- |
| **REST_API_Manager** | `register()` вешает `rest_api_init`; `register_routes()` подключает контроллеры через `require` и вызывает их | Маршруты `cpm/v1/*` зарегистрированы после `rest_api_init` (проверка через `rest_get_server()->get_routes()`) |
| **Регистрация маршрутов сущности** | Для каждого типа зарегистрированы 4 CRUD-маршрута (список/одна/создание/обновление/удаление) | Реальные запросы к маршрутам проходят через контроллер |
| **Сериализация** (`prepare_item_for_response`) | Сущность (мок с декоратором) → ожидаемый массив по `схемы.md`; контент отдаётся как есть; team → карта `{user_id: role}`; даты в формате ядра | Ответы реальных GET соответствуют схеме |
| **Список / одна сущность** | `get_items()` передаёт в `load_list()` параметры-фильтры из запроса; `get_item()` при пустом результате → 404 | GET списка возвращает JSON-массив + заголовки `X-WP-Total`/`X-WP-TotalPages` (после доработки ядра); GET по несуществующему/недоступному id → 404 |
| **Создание/обновление/удаление** | `create_item()` вызывает `Core_Manager::create()`; update применяет только разрешённые поля и зовёт `save()`; delete зовёт `delete()` | POST создаёт (201), повторный GET отдаёт; update меняет поля; delete удаляет и возвращает 204 |
| **Экшены** (`archive`, `team`, `thumbnail`, …) | Экшен загружает сущность, валидирует своё тело, вызывает действие ядра; при пустой `load_list()` → 404 | POST `/project/{id}/archive` переводит в архив; `/team` меняет участников; ответ — 200 с обновлённым объектом |
| **Маппинг ошибок** | `AccessDeniedException` → 403 `cpm_forbidden`; пустой `load_list()` → 404 `cpm_not_found`; `EntitySaveException` → 500 `cpm_save_failed`; ошибка валидации → 400 | Реальный запрет (CLIENT удаляет проект и т.п.) → корректный код |
| **Валидация параметров** | Неверный тип id/фильтра → 400; неизвестное и read-only поле в теле → 400 (решения №17–18) | — |
| **Аутентификация** | — | Без nonce/учётки → 401/403 (штатный WordPress) |
| **Attachment /file** | Контроллер файла: пустой `load_list()` → 404; правильные заголовки `Content-Type` | GET `/attachment/{id}/file` отдаёт бинарник; CLIENT → 404 |

## Сквозные сценарии

| Сценарий | Уровень |
| -------- | ------- |
| **Таблица прав через REST**: пользователь с ролью CLIENT не видит вехи/вложения (404/пустой список); MANAGER видит и изменяет проект (200); CO_WORKER читает чужую задачу и не может её изменить (403) | [I] |
| **Фильтрация по проекту**: список задач с `?project_id=` возвращает только задачи проекта | [I] |
| **Round-trip сущности**: POST → GET → POST(update) → DELETE дают согласованные ответы | [I] |

## Правило соответствия

- Реализация каждого контроллера сопровождается тестами из матрицы.
- Контроллеры — только регистрация маршрутов, сериализация и маппинг ошибок: тесты не должны мокать поведение ядра (оно покрыто отдельно), а лишь проверять корректное делегирование.
- Изменение схемы (`схемы.md`) или маппинга ошибок (`права-и-ошибки.md`) влечёт обновление соответствующих тестов в том же изменении.

## Окружение для интеграционных тестов

- Маршруты регистрируются на `rest_api_init` — в тестах используется реальный `WP_REST_Server` (`rest_get_server()`).
- Аутентификация в тестах — через установку текущего пользователя (`wp_set_current_user()`) и, при необходимости, nonce.
- Интеграционные тесты REST выполняются на стенде Docker с тестовой БД `cpm_test` (`tests/конфигурация.md`).
