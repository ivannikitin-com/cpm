# Маршруты REST API CPM v3 (namespace `cpm/v1`)

Документ описывает все маршруты модуля. Регистрируются контроллерами через `register_rest_route()` (см. `архитектура.md`).

## Базовый URL

```
{rest_url}/cpm/v1/...
```

где `{rest_url}` — стандартный корень REST WordPress (`site_url()/wp-json`). Версия API — **часть URL** (`cpm/v1`): при несовместимых изменениях добавляется `v2`, старый namespace продолжает работать в режиме совместимости.

## Общая схема маршрутов для сущности

Каждая сущность ядра (тип `$type` из `get_type()`: `project`, `task_list`, `task`, `message`, `milestone`, `note`, `comment`, `attachment`, `activity`) получает четыре стандартных маршрута. Дополнительно для вложений — маршрут файла.

| Метод | Путь | Назначение | Контроллер |
| ----- | ---- | ---------- | ---------- |
| `GET` | `/cpm/v1/{type}` | Список сущностей (с фильтрами) | `get_items()` |
| `POST` | `/cpm/v1/{type}` | Создание сущности | `create_item()` |
| `GET` | `/cpm/v1/{type}/{id}` | Одна сущность | `get_item()` |
| `POST` | `/cpm/v1/{type}/{id}` | Обновление сущности | `update_item()` |
| `DELETE` | `/cpm/v1/{type}/{id}` | Удаление сущности | `delete_item()` |

Сегмент `{type}` в URL совпадает со строкой типа сущности ядра (snake_case): `cpm/v1/task_list/123`.

> **Права**: маршруты регистрируются для всех сущностей, но фактический доступ определяет ядро. Например, `DELETE /cpm/v1/task_list/{id}` вернёт `403`, если пользователь не имеет права модификации списка задач (декоратор `ReadOnly_Decorator` выбрасывает `AccessDeniedException`). Права на запись/удаление не дублируются в контроллерах.

## Таблица сущностей и маршрутов

| Тип (`get_type()`) | URL-префикс | Создание | Чтение | Обновление | Удаление | Особенности |
| ------------------ | ----------- | -------- | ------ | ---------- | -------- | ----------- |
| `project` | `/cpm/v1/project` | да | да | да | **только ADMINISTRATOR** (ядро) | удаление проекта — прерогатива администратора (`docs/core/project.md`) |
| `task_list` | `/cpm/v1/task_list` | да | да | да* | да* | *фактически только для администратора; для остальных ролей сущность только для чтения |
| `task` | `/cpm/v1/task` | да | да | да | да | — |
| `message` | `/cpm/v1/message` | да | да | да | да | — |
| `milestone` | `/cpm/v1/milestone` | да | да | да | да | для CLIENT `no_access` (ядро исключает из выборки) |
| `note` | `/cpm/v1/note` | да | да | да | да | — |
| `comment` | `/cpm/v1/comment` | да | да | да | да | только `modify_own` (автор) |
| `attachment` | `/cpm/v1/attachment` | да (multipart) | да | да | да | для CLIENT `no_access`; плюс маршрут `/file` |
| `activity` | `/cpm/v1/activity` | **нет** | да | **нет** | **нет** | журнал действий, только чтение |

> Создание записи `activity` через REST невозможно в принципе: ядро запрещает `create('activity')` (`core_manager.php`), записи создаёт сам класс `Activity` по хукам ядра.

## Параметры списка (`GET /cpm/v1/{type}`)

Параметры коллекции соответствуют фильтрам, которые ядро умеет подставлять в SQL (`docs/core/core-manager.md`, `$having_filters`). Контроллер передаёт их в `load_list()` как `$args`; контроллер принимает только известные параметры, недопустимое значение известного параметра → `400` (см. `права-и-ошибки.md`).

| Параметр | Тип | Назначение | Примечание |
| -------- | --- | ---------- | ---------- |
| `id` | int | Фильтр по ID | обычно используется внутренним запросом одной сущности |
| `parent` | int | Сущности с указанным родителем | например, задачи одного списка задач, комментарии сущности |
| `project_id` | int | Сущности указанного проекта | ключевой фильтр для дочерних сущностей проекта |
| `task_list_id` | int | Задачи указанного списка задач | только для `task` |
| `slug` | string | Фильтр по слагу | |
| `orderby` / `order` | string | Сортировка | по свойствам сущности (см. `схемы.md`); по умолчанию порядок SQL-запроса сущности (`menu_order`, `title` и т.п.) |
| `context` | string | `view` (по умолчанию) / `edit` | `edit` не добавляет прав: права определяет ядро |

Список поддерживаемых фильтров по каждому типу фиксируется в схеме коллекции контроллера (`схемы.md`).

### Пагинация

Списки могут быть большими (например, журнал `activity`), поэтому используются стандартные параметры WP REST:

| Параметр | По умолчанию | Назначение |
| -------- | ------------ | ---------- |
| `page` | `1` | Номер страницы |
| `per_page` | `20` (макс. `100`) | Размер страницы |
| `offset` | — | Сдвиг от начала (альтернатива `page`) |

**Решение**: пагинация поддерживается; ответ списка включает заголовки `X-WP-Total` и `X-WP-TotalPages`. Поддержка требует доработки ядра — добавления `LIMIT`/`OFFSET` и подсчёта общего числа строк в выборку `load_list()` (`docs/core/выборка-sql.md`, `docs/core/core-manager.md`). До этой доработки контроллер списка возвращает всю выборку.

### Сортировка

Параметры `orderby` / `order` передаются в ядро и поддерживаются на уровне SQL-выборки. **Решение**: допустимые поля сортировки и их передача в `load_list()` дорабатываются в ядре; контроллер списка принимает `orderby` по свойствам сущности (см. `схемы.md`) и `order` = `asc`/`desc`. Значение по умолчанию — порядок, заданный SQL-запросом сущности (`menu_order`, `title` и т.п.).

## Особые маршруты

### Маршруты-экшены

Действия ядра, не сводимые к записи полей общего update, оформляются **отдельными маршрутами-экшенами** (решение №20–22 в `открытые-вопросы.md`):

| Метод | Путь | Назначение | Действие ядра |
| ----- | ---- | ---------- | ------------- |
| `POST` | `/cpm/v1/project/{id}/archive` | Перевести проект в архив | `Project::archive()` |
| `POST` | `/cpm/v1/project/{id}/unarchive` | Вернуть проект в активные | `Project::unarchive()` |
| `POST` | `/cpm/v1/project/{id}/coordinator` | Назначить координатора | `Project::set_coordinator( $user_id )` |
| `POST` | `/cpm/v1/project/{id}/team` | Изменить команду проекта | изменение `Team` проекта (см. ниже) |
| `POST` | `/cpm/v1/{type}/{id}/thumbnail` | Установить картинку сущности | `Entity::set_thumbnail( $attachment_id )` |

Экшены принимают минимальное тело: например, `{ "user_id": 12 }` для `coordinator`, `{ "members": { "12": "manager", "15": "client" } }` для `team`, `{ "thumbnail_id": 55 }` для `thumbnail`. Точный формат тела фиксируется в контроллерах при реализации.

> `team` у дочерних сущностей проекта (исполнители задачи, дефолтовые участники списка) меняется по тем же правилам, что у проекта, но через экшен **соответствующей сущности** (`/cpm/v1/task/{id}/team` и т.п.), а не проекта.

### Бинарный файл вложения

Прототип в `docs/core/attachment.md` предполагал, что `GET /attachment/{id}` отдаёт бинарный файл. **Решение модуля REST API**: отделить метаданные от содержимого, чтобы сохранить единый CRUD-контроллер:

| Метод | Путь | Назначение |
| ----- | ---- | ---------- |
| `GET` | `/cpm/v1/attachment/{id}` | JSON-объект вложения (метаданные: имя, mime, размеры) |
| `GET` | `/cpm/v1/attachment/{id}/file` | Содержимое файла (бинарные данные) с корректным `Content-Type` |
| `GET` | `/cpm/v1/attachment/{id}/file?size=thumbnail` | Файл-изображение в указанном размере миниатюры |
| `GET` | `/cpm/v1/attachment/{id}/file?download=1` | То же, но с `Content-Disposition: attachment` (скачивание) |

Проверка прав — в ядре: контроллер получает вложение через `load_list('attachment', array('id' => $id))`; для `CLIENT` ядро вернёт пустой результат → `404`. Файлы читаются вне зависимости от физического расположения (старая `uploads/` или новая приватная `uploads/cpm/`) — см. `загрузка-файлов.md`.

### Создание вложения (multipart)

`POST /cpm/v1/attachment` принимает данные не как JSON, а как `multipart/form-data` (сам файл + поля привязки). Подробно: `загрузка-файлов.md`.

## Структура ответов

- **Список**: массив объектов в корне ответа (без обёртки) + заголовки `X-WP-Total` / `X-WP-TotalPages`.
- **Одна сущность / создание / обновление**: объект сущности. Для создания — HTTP `201 Created`.
- **Удаление**: HTTP `204 No Content`.
- **Ошибки**: `WP_Error` → JSON с `code`, `message`, `data.status` (HTTP-код). Полный словарь — `права-и-ошибки.md`.
