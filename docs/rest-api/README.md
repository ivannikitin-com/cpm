# Модуль REST API CPM v3

Спецификации модуля REST API (перенос/дистилляция заметок Obsidian). Обязательны к прочтению перед работой над любым классом модуля: `source/classes/rest_api/`.

Модуль REST API — слой интеграции CPM v3 с внешними сервисами и с собственным UI. UI — это React-приложение, которое **работает только через REST API** (`docs/07-модуль-ui.md`), поэтому REST API — единственный публичный интерфейс CPM v3 поверх ядра.

## Ключевые принципы модуля

1. **REST API — тонкий слой.** Контроллеры не содержат бизнес-логики: они преобразуют HTTP-запрос в вызов фабрики ядра (`Core_Manager::load_list()` / `create()`), сериализуют ответ и переводят исключения ядра в HTTP-ответы. Вся логика, права и SQL — в ядре.
2. **Права — только ядром.** Контроллер не проверяет права сам: сущности приходят из `load_list()` уже обёрнутыми декоратором по роли текущего пользователя, а запрещённая операция выбрасывает `AccessDeniedException`. Слой REST лишь ловит исключение и превращает его в HTTP-ответ (403/404). См. `права-и-ошибки.md`.
3. **Классы REST грузятся лениво.** Классы контроллеров подключаются через `require()` только при обработке REST-запроса (`rest_api_init`), а не на каждом запросе. Никакого автозагрузчика (см. `docs/09-стандарты-кодирования.md`).
4. **Единый namespace и формат.** Все маршруты — в namespace `cpm/v1` (базовый URL `{rest_url}/cpm/v1`), ответы — JSON. Имена полей соответствуют свойствам сущностей ядра (snake_case), чтобы исключить двойной словарь.
5. **Ответы отдаёт ядро/сериализатор, а не контроллер.** Контроллер собирает из сущности (объект, обёрнутый декоратором) ассоциативный массив через единый сериализатор (`схемы.md`).

## Ключевые принятые решения (зафиксировано)

| № | Тема | Решение |
| -- | ---- | ------- |
| 1 | Namespace маршрутов | `cpm/v1`; версия API в URL (`/wp-json/cpm/v1/...`) |
| 2 | Права в REST | Только через ядро (декораторы); контроллер не дублирует проверки |
| 3 | Ответ на запрет | `AccessDeniedException` → HTTP `403`; недоступная сущность выглядит как `404` |
| 4 | Отсутствие сущности | `load_list()` вернул пустой массив → HTTP `404` |
| 5 | Единичная сущность | Через `load_list()` с фильтром `id` (массив из 1 элемента), без отдельного метода чтения |
| 6 | Загрузка контроллеров | `require()` по хуку `rest_api_init` |
| 7 | Аутентификация | Cookie + nonce для UI; Application Passwords для внешних сервисов (`аутентификация.md`) |
| 8 | Бинарные файлы | `GET /cpm/v1/attachment/{id}/file` — содержимое файла; `GET /cpm/v1/attachment/{id}` — JSON объекта (см. `маршруты.md`, расходится с прототипом в `docs/core/attachment.md`) |
| 9 | Формат ответов списков | Массив объектов в корне ответа (без обёртки-объекта) + заголовки пагинации `X-WP-Total*` |
| 10 | Контент сущностей | Отдаётся как хранится (Markdown/HTML/шорткоды); парсинг — зона UI (`docs/core/контент-сущностей.md`) |

> Полный реестр решений и открытых вопросов модуля (включая решения по контроллерам, пагинации, датам, экшенам, удалению, API-ключу) — в `открытые-вопросы.md`.

## Классы модуля (пространство имён `\CPM\v3\REST\`)

Контроллеры наследуют штатный `WP_REST_Controller` (решение №12, `открытые-вопросы.md`).

| Класс | Файл | Назначение | Спецификация |
| ----- | ---- | ---------- | ------------ |
| `REST_API_Manager` | `rest_api/rest_api_manager.php` | Менеджер модуля: регистрация маршрутов, загрузка контроллеров | `архитектура.md` |
| `Base_Controller` (abstract, extends `WP_REST_Controller`) | `rest_api/class-base-controller.php` | Общая логика контроллера: доступ к ядру, подготовка ответа, обработка ошибок | `архитектура.md` |
| `Entity_Controller` (abstract, extends `Base_Controller`) | `rest_api/class-entity-controller.php` | Базовый CRUD-контроллер одной сущности: register_routes(), list/create/get/update/delete | `архитектура.md`, `маршруты.md` |
| Контроллеры сущностей (`Project_Controller`, `Task_Controller`, …) | `rest_api/` | Конкретные контроллеры: схема полей, аргументы, экшены, особые маршруты (вложения — файл) | `маршруты.md`, `схемы.md` |

Конкретный перечень файлов и имён уточняется при реализации (см. `открытые-вопросы.md`).

## Зависимости от ядра (порядок работ)

Все четыре доработки ядра, которые блокировали REST, **реализованы**:

1. **Пагинация и сортировка в `load_list()`** — реализовано в `Core_Manager::load_list()` (`page`/`per_page`/`offset`, `orderby`/`order` по белому списку колонок типа) + новый `Core_Manager::count_list()` для общего числа (решения №14–15). См. `docs/core/core-manager.md`.
2. **Механизм загрузки вложений в ядре** — `Attachment::validate_upload()` и `Attachment::create_from_upload()` (whitelist MIME, лимит размера, `uploads/cpm/`, мета `_project`/`_parent`, привязка `commentmeta._files`). См. `docs/core/attachment.md`, `загрузка-файлов.md`.
3. **Комментарии** — чтение через ядро дополнено пагинацией/сортировкой и `query_count()` (`docs/core/comment.md`).
4. **Activity** — набор хуков зафиксирован (лог всех мутаций сущностей проекта, кроме activity и без проекта); чтение дополнено пагинацией/сортировкой и `query_count()` (`docs/core/activity.md`).

REST-модуль (регистрация маршрутов, сериализация, маппинг ошибок, экшены, валидация, аутентификация) может реализовываться и покрываться тестами, как только появится первый реализованный контроллер.

## Как работать с этими документами

1. Прочитайте `архитектура.md` — место модуля, менеджер, загрузка классов.
2. При работе над маршрутом/контроллером конкретной сущности — `маршруты.md` и `схемы.md`.
3. Перед реализацией обработки ошибок — `права-и-ошибки.md` и `docs/core/ошибки.md`.
4. Проверьте `открытые-вопросы.md` и `docs/core/открытые-вопросы.md` — не решено ли что-то иначе.
5. Для каждого контроллера добавляйте тесты по матрице `тесты.md` и `tests/покрытие.md`.
