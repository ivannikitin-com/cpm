# Обработка ошибок CPM

В документации обработка ошибок описана фрагментарно (см. `BadUserException` в `user.md`). Этот документ систематизирует её.

## Иерархия исключений

Единый базовый класс и наследники:

```
CPM_Exception (abstract)          — базовый класс всех исключений ядра
 ├── BadUserException             — пользователь не найден при загрузке (User::load())
 ├── AccessDeniedException        — пользователю запрещено действие над сущностью (декоратор)
 └── EntitySaveException          — ошибка сохранения/удаления в БД
```

| Класс | Когда выбрасывается |
| ----- | ------------------- |
| `CPM_Exception` | Абстрактный базовый класс всех исключений ядра |
| `BadUserException` | Пользователь не найден при загрузке (`User::load()`) |
| `AccessDeniedException` | Пользователю запрещено действие над сущностью (декоратор) |
| `EntitySaveException` | Ошибка сохранения/удаления в БД |

## Сценарии и поведение

### 1. Пользователь не найден — `BadUserException`

`User::load()` выбрасывает `BadUserException`, если пользователь с указанным `id` не найден в WordPress.

### 2. Запрет доступа — `AccessDeniedException`

Декораторы (`Base_Decorator`) проверяют `can_modify()`. Если операция запрещена:

- **Решение**: ядро выбрасывает `AccessDeniedException` и **не выполняет** операцию (сохранение/удаление/изменение свойств не происходит).
- Что происходит дальше и как это показывается пользователю, решает **модуль интерфейса (UI)** или слой REST: скрыть кнопку, вывести сообщение, вернуть HTTP-код `403` и т.п. Ядро на это не влияет — оно лишь сигнализирует о запрете через исключение.
- Молчаливый no-op (возврат без изменений) **не используется**: он скрывает ошибки в логике вызова и усложняет отладку.

### 3. Сущность не найдена / отсутствует

- `get_project()` возвращает `null` для сущности, не принадлежащей проекту. В этом случае `ACL::get_role()` возвращает `NO_ROLE` — это штатное поведение, не ошибка.
- `load_list()` всегда возвращает массив; при отсутствии записей — пустой массив, а не ошибку.

### 4. Ошибка сохранения в БД — `EntitySaveException`

`wp_insert_post()` / `wp_update_post()` при ошибке могут вернуть `0` или `WP_Error`. Реализация `save()` в `Entity` должна проверять результат и выбрасывать `EntitySaveException` при неудаче.

### 5. Ошибка прав как граница безопасности

Проверка прав выполняется в двух местах:

- **На уровне выборки** — фильтр по пользователю в SQL (для `administrator` — без фильтра).
- **На уровне декораторов** — при попытке изменить сущность.

Это даёт защиту в глубину: даже если сущность попала в выборку, запись/удаление всё равно контролируется декоратором.

## Рекомендации

- Все исключения наследовать от `CPM_Exception`, чтобы вызывающий код мог перехватывать их одним блоком.
- Верхний слой (обработчики запросов / REST) перехватывает `CPM_Exception` и превращает его в понятный пользователю ответ (например, HTTP-код `403` для `AccessDeniedException`, `404` для отсутствующей сущности).
- Логировать неожиданные сбои (не связанные с правами пользователя).
