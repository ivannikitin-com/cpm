# Сущности ядра: IEntity, Entity, Project_Entity

Три взаимосвязанных типа: интерфейс `IEntity`, базовый абстрактный класс `Entity` и абстрактный класс `Project_Entity` (сущность проекта).

## Интерфейс IEntity

Определяет основные методы классов сущностей:

```php
interface IEntity {
	public function get_project();        // возвращает Project, которому принадлежит сущность (или пусто)
	public function save();               // сохраняет объект в БД
	public function delete( $is_recursion = false );  // удаляет объект из БД
}
```

## Класс Entity

Реализует общие свойства и методы для всех сущностей CPM v3, реализует интерфейс `IEntity`.

### Свойства

| Свойство | Тип | Назначение |
| -------- | --- | ---------- |
| `id` | int | Идентификатор сущности |
| `parent` | int | ID родительского элемента (у задачи родитель — список задач; может указывать на проект или другую задачу — см. `task.md`) |
| `author` | int | ID автора сущности (для проверки прав редактирования своих элементов) |
| `title` | string | Заголовок сущности |
| `content` | string | Текстовое содержимое сущности (форматы — `контент-сущностей.md`) |
| `created_at` | string | Дата создания сущности |
| `slug` | string | Слаг сущности (часть URL) |
| `menu_order` | int | Позиция для сортировки в интерфейсе |
| `thumbnail_id` | int | ID вложения WordPress (attachment), используемого как картинка/логотип сущности. Хранится в стандартном мета-поле `_thumbnail_id` (featured image). `0` = нет картинки |
| `team` | Team | Команда (пользователи) сущности, экземпляр `Team` |

### Методы

| Метод | Назначение |
| ----- | ---------- |
| конструктор `__construct($args)` | Аргументы — массив, описан в `core-manager.md` |
| `get_type()` | Возвращает тип сущности строкой в нижнем регистре |
| `get_project()` | Возвращает экземпляр `Project`; в `Entity` — абстрактный |
| `set_thumbnail($attachment_id)` | Устанавливает картинку и немедленно сохраняет |
| `get_thumbnail_id()` | Возвращает ID вложения-картинки |
| `get_thumbnail_url($size)` | Возвращает URL картинки указанного размера |
| `get_thumbnail($size)` | Ищет картинку по цепочке родительства, возвращает URL или пустую строку |
| `get_wp_args()` (protected) | Массив аргументов с именами WordPress для `wp_insert_post()`/`wp_update_post()` |
| `save()` | Сохраняет сущность в БД; вызывает хуки WordPress (`хуки-события.md`) |
| `delete($is_recursion=false)` | Рекурсивно удаляет из БД дочерние сущности и саму сущность; вызывает хуки WordPress |
| `delete_entity()` (protected) | Собственно удаление конкретной сущности; может быть перекрыт потомками |

### Реализация `get_type()`

Возвращает строкой тип сущности в нижнем регистре, например: `project`, `task_list`, `task`. Метод необходим для точного определения типа, так как реальные объекты могут быть обёрнуты декораторами, и чтение класса объекта может вернуть неверные данные.

Возможная реализация (общая на уровне `Entity`):

- используется позднее статическое связывание;
- считывается название класса `static::class`;
- из строки убирается префикс пространства имён;
- строка приводится к нижнему регистру.

### Реализация `get_wp_args()`

Формирует массив аргументов для `wp_update_post()` на основе полей объекта. Для сущностей на основе CPT метод переопределяется для добавления CPT.

Пример:

```php
protected function get_wp_args() {
	return array(
		'ID'             => $this->id,
		'menu_order'     => $this->menu_order,
		'post_author'    => $this->author,
		'post_content'   => $this->content,
		'post_date'      => $this->created_at,
		'post_name'      => $this->slug,
		'post_parent'    => $this->parent,
		'post_status'    => 'publish',
		'post_title'     => $this->title,
		'meta_input'     => array(
			'_team'         => $this->team->get_members(),
			'_thumbnail_id' => $this->thumbnail_id,
		),
	);
}
```

### Реализация `save()`

Сохраняет информацию о сущности в БД. Использует штатные функции WordPress: `wp_update_post()` для существующей записи или `wp_insert_post()` для новой (новая запись определяется по `$this->id === 0`). По умолчанию реализация для сущностей на базе CPT; для других типов (например, комментариев) переопределяется. После обновления данных обязательно вызывается `flush()` у `Core_Manager`.

```php
public function save() {
	// Проверка нового объекта, отсутствующего в БД
	if ( empty( $this->id ) ) {
		// Это новый объект, создаём запись в БД
		$this->id = wp_insert_post( wp_slash( $this->get_wp_args() ) );
	}
	else {
		// Обновление записи в БД
		wp_update_post( wp_slash( $this->get_wp_args() ) );
	}

	// Сброс кэша
	Core_Manager::get_instance()->flush();
}
```

При сохранении также выполняются события `cpm_core_entity_create` / `cpm_core_entity_update` (детали — `хуки-события.md`).

### Реализация `delete()`

Рекурсивно удаляет из БД все дочерние сущности для текущей и саму сущность. Сначала запрашиваются дочерние сущности у `Core_Manager` и для каждой вызывается `delete(true)` — признак того, что это шаг вложенной рекурсии. Это ресурсоёмкая, но редкая операция.

При рекурсивном удалении для каждого дочернего элемента проверка прав и т.п. должна максимально использовать кэши, чтобы снизить нагрузку на БД. Для этого используется аргумент `$is_recursion` (по умолчанию `false`). При значении `true` после удаления **не** вызывается `flush()` у `Core_Manager` — кэши сбрасываются только после полного завершения рекурсии.

```php
// Дочерние сущности
$child_entities = Core_Manager::get_instance()->load_list( array(
	'parent' => $this->id,
) );

// Удаление дочерних сущностей
foreach ( $child_entities as $child ) {
	$child->delete( true );
}

// Удаление текущей сущности
$this->delete_entity();

// Если это шаг рекурсии, кэши не сбрасываются
if ( ! $is_recursion ) {
	Core_Manager::get_instance()->flush();
}
```

При удалении также выполняется событие `cpm_core_entity_delete` (только для корневой сущности) — детали в `хуки-события.md`.

### Реализация `delete_entity()`

Стандартный способ удаления сущности как `post` WordPress. Применимо практически для всех типов сущностей, но может быть перекрыто потомками (например, для комментария).

```php
wp_delete_post( $this->id, CPM_FORCE_DELETE );
```

Константа `CPM_FORCE_DELETE` устанавливается в основном коде плагина и по умолчанию равна `true` — удаление без помещения в корзину.

## Картинка сущности (featured image)

### Идея

Все сущности ядра CPM (проект, список задач, задача, веха, сообщение), кроме комментариев, имеют свойство картинки (логотипа). Для этого используется стандартное свойство **featured image** записи WordPress.

Свойство размещается в базовом классе `Entity`, так как:

- все перечисленные сущности — CPT-сущности и наследуют общий механизм сохранения через `get_wp_args()` → `wp_insert_post()` / `wp_update_post()`. Картинка ложится в эту общую точку и не дублируется в каждом классе;
- комментарию это не помешает: класс `Comment` полностью переопределяет `save()`, `get_wp_args()` и `delete_entity()` под таблицу `comments` WordPress. Унаследованное свойство `thumbnail_id` просто останется неиспользуемым.

### Хранение

Картинка хранится как **ID вложения** в стандартном мета-поле `_thumbnail_id`:

- это ровно то, что WordPress понимает как featured image (`set_post_thumbnail()`, `get_post_thumbnail_id()`, `has_post_thumbnail()`), со встроенными размерами изображений;
- REST API, AJAX-обработчики и темы из коробки читают именно `_thumbnail_id`;
- не следует хранить URL строкой в собственном мета-поле — это сломает совместимость с нативным API WordPress.

### Реализация в `get_wp_args()`

В массив `meta_input` добавляется ключ `_thumbnail_id` (см. пример выше). Потомки, переопределяющие `get_wp_args()` через `array_merge` с `parent::get_wp_args()` (например, `Project`), подхватывают это автоматически.

### Чтение из БД

В SQL-выборку каждой CPT-сущности добавляется строка по типовому паттерну:

```sql
MAX(CASE WHEN pm.meta_key = '_thumbnail_id' THEN pm.meta_value ELSE NULL END) AS thumbnail_id
```

### Сервисные методы

```php
// Установка картинки и немедленное сохранение
public function set_thumbnail( $attachment_id ) {
	$this->thumbnail_id = $attachment_id;
	$this->save();
}

// Получение ID вложения
public function get_thumbnail_id() {
	return $this->thumbnail_id;
}

// Получение URL картинки указанного размера, удобно для UI и REST
public function get_thumbnail_url( $size = 'full' ) {
	if ( empty( $this->thumbnail_id ) ) {
		return '';
	}
	return wp_get_attachment_image_url( $this->thumbnail_id, $size );
}
```

### Метод `get_thumbnail()` — поиск картинки по цепочке родительства

Скрывает всю логику поиска картинки: возвращает либо URL картинки, либо пустую строку.

Логика:

1. Считывается `thumbnail_id` текущей сущности.
2. Если картинка не установлена, поиск продолжается по цепочке родительства: у родительской сущности (у задачи — список задач, у списка — проект), затем у родителя родителя и так далее вплоть до проекта.
3. Если картинка не найдена и у проекта (корня цепочки) — возвращается пустая строка.
4. Если ID найден — вызывается `get_thumbnail_url()` и возвращается URL.

```php
public function get_thumbnail( $size = 'full' ) {
	$thumbnail_id = $this->find_thumbnail_id();

	if ( empty( $thumbnail_id ) ) {
		return '';
	}

	return wp_get_attachment_image_url( $thumbnail_id, $size );
}

protected function find_thumbnail_id() {
	$entity = $this;

	while ( $entity ) {
		if ( ! empty( $entity->thumbnail_id ) ) {
			return $entity->thumbnail_id;
		}
		$entity = $entity->get_parent_entity();
	}

	return 0;
}
```

Замечание о подъёме по цепочке: свойство `parent` хранит только ID родителя, поэтому для перехода к родительской сущности необходимо её загрузить. Для сущностей проекта достаточно ограничиться `project_id` и загрузить сам проект, так как цепочка всегда заканчивается проектом. У комментариев метод всегда вернёт пустую строку.

### Удаление

При `delete_entity()` вложение **не удаляется**: `wp_delete_post()` с `CPM_FORCE_DELETE` не трогает attachment. Одна картинка может переиспользоваться несколькими сущностями (например, один логотип у проекта и его вех). Логику удаления файла добавлять не требуется.

## Класс Project_Entity

Абстрактный класс сущности проекта для сущностей, которые **всегда принадлежат какому-то проекту** (например, `Task_List`, `Task`).

### Свойства

| Свойство | Тип | Назначение |
| -------- | --- | ---------- |
| `project_id` | int | ID проекта, которому принадлежит сущность |
| `project_title` | string | Название проекта `title`. Записывается при создании сущности, чтобы при выводе (e-mail, оповещения) не создавать проект ради одного поля названия |
| `project_slug` | string | Слаг проекта (нужен, чтобы формировать URL без доп. обращений к БД) |

### Реализация `get_project()`

Права пользователя при работе с сущностями проекта задаются на уровне проекта: команда проекта `Team` используется в том числе для проверки прав (добавить комментарий, создать задачу и т.п.). Любой сущности проекта надо знать и быстро получать команду проекта.

`project_id` заполняется на этапе создания сущности. При необходимости проверки прав вызывается `get_project()`, который на основании `project_id` создаёт (возможно, из кэша) экземпляр проекта и возвращает его. Так сокращается память: реально хранится только ID проекта.
