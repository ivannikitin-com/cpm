# События CPM (хуки WordPress)

Система событий ядра CPM v3, построенная на штатных хуках WordPress (`do_action` / `apply_filters`). События нужны, чтобы другие компоненты CPM (интерфейс, расширения) могли получать уведомления о действиях с сущностями — например, расширение отправляет уведомление в почту или мессенджер при создании новой задачи.

## Принципы

- События делятся на два типа по назначению:
  - **`do_action` (уведомления)** — оповещают о том, что действие произошло. Используются для побочных эффектов: письма, мессенджеры, аудит, синхронизация.
  - **`apply_filters` (данные)** — позволяют модифицировать данные до/после обработки. Используются для изменения контента, аргументов, отдаваемых данных.
- Хуки на **мутации** (create/update/delete) вешаются в классе `Entity`, потому что все сущности наследуют от него общие методы `save()` и `delete()` — это единая точка прохождения любой операции изменения любой сущности.
- **`Activity`** — ключевой потребитель событий: он автоматически ведёт журнал действий, подписываясь на `cpm_core_entity_*` и записывая записи лога.
- Хук на **чтение** на уровне `Entity` **не выполняется** (см. раздел «Чтение»).
- Событие передаёт **полный объект сущности** (обёрнутый декоратором), а не голый `id`. Подписчику не нужно заново загружать сущность и повторно разбираться с правами.

## Область применения

События ядра покрывают все сущности, наследующие `Entity`: проект, список задач, задача, веха, сообщение, заметка. Комментарии (`Comment`) также наследуют `Entity` и переопределяют `save()`/`delete()`, поэтому для них события срабатывают в переопределённых методах.

## Именование хуков

Единый формат:

```
cpm_core_entity_{операция}
```

Дополнительно для каждого типа сущности — типизированный вариант (чтобы подписчик мог подписаться сразу на конкретный тип):

```
cpm_core_entity_{операция}_{тип}
```

где `{тип}` — строка типа сущности из `get_type()`: `project`, `task_list`, `task`, `milestone`, `message`, `note`.

Примеры:

- `cpm_core_entity_create` — событие создания любой сущности.
- `cpm_core_entity_create_task` — событие создания именно задачи.

## Хуки на мутации

### Создание — `cpm_core_entity_create`

Выполняется в методе `save()` сразу после `wp_insert_post()` для новой записи (когда `$this->id` был `0` до сохранения).

| Хук | Аргументы |
| --- | --- |
| `cpm_core_entity_create` | `$entity` |
| `cpm_core_entity_create_{type}` | `$entity` |

### Обновление — `cpm_core_entity_update`

Выполняется в методе `save()` после `wp_update_post()` для существующей записи.

| Хук | Аргументы |
| --- | --- |
| `cpm_core_entity_update` | `$entity` |
| `cpm_core_entity_update_{type}` | `$entity` |

### Удаление — `cpm_core_entity_delete`

Выполняется в методе `delete()` **до** фактического удаления (`delete_entity()`). Это позволяет подписчику собрать уведомление «Сущность X удалена», пока в свойствах объекта ещё доступны `id`, `title`, `parent` и т.п.

| Хук | Аргументы |
| --- | --- |
| `cpm_core_entity_delete` | `$entity` |
| `cpm_core_entity_delete_{type}` | `$entity` |

### Порядок вызова типизированного и общего хуков

Для каждого события вызываются оба хука: сначала типизированный, затем общий:

```php
do_action( "cpm_core_entity_create_{$type}", $this );
do_action( 'cpm_core_entity_create', $this );
```

Такой порядок (от частного к общему) позволяет сначала обработать специфичную логику, затем общую.

## Чтение

Хук-уведомление на чтение на уровне `Entity` **не создаётся**. Причины:

- Чтение — самый горячий путь (списки задач, отрисовка интерфейса). Вызов `do_action()` на каждый загруженный объект означает вызов по каждому объекту списка; даже без слушателей WordPress проходит цепочку хука, что даёт лишние накладные расходы при загрузке сотен сущностей.
- У `Entity` нет метода чтения: объекты создаются фабрикой `Core_Manager::load_list()` из SQL. Если в будущем потребуется событие на чтение, его следует встраивать в `load_list()` — одно событие на выборку, а не на объект — и, скорее всего, как **`apply_filters`** (модификация данных перед отдачей), а не как `do_action`-уведомление.

## Реализация в классе Entity

### В методе `save()`

```php
public function save() {
	// Проверка нового объекта
	if ( empty( $this->id ) ) {
		// Создание новой записи
		$this->id = wp_insert_post( wp_slash( $this->get_wp_args() ) );
		$is_new = true;
	}
	else {
		// Обновление существующей записи
		wp_update_post( wp_slash( $this->get_wp_args() ) );
		$is_new = false;
	}

	// События: сначала типизированный, затем общий хук
	$type  = $this->get_type();
	$event = $is_new ? 'create' : 'update';

	do_action( "cpm_core_entity_{$event}_{$type}", $this );
	do_action( "cpm_core_entity_{$event}", $this );

	// Сброс кэша
	Core_Manager::get_instance()->flush();
}
```

### В методе `delete()`

Хук вешается **до** `delete_entity()`, чтобы у подписчика были актуальные данные об удаляемой сущности:

```php
public function delete( $is_recursion = false ) {
	// Дочерние сущности
	$child_entities = Core_Manager::get_instance()->load_list( array(
		'parent' => $this->id,
	) );

	// Событие удаления до фактического удаления сущности.
	// На вложенных шагах рекурсии событие не вызывается, чтобы подписчики
	// получали уведомление только о корневой удаляемой сущности.
	if ( ! $is_recursion ) {
		$type = $this->get_type();
		do_action( "cpm_core_entity_delete_{$type}", $this );
		do_action( 'cpm_core_entity_delete', $this );
	}

	// Удаление дочерних сущностей
	foreach ( $child_entities as $child ) {
		$child->delete( true );
	}

	// Удаление текущей сущности
	$this->delete_entity();

	// Если это шаг рекурсии, кэши не сбрасываются
	if ( ! $is_recursion ) {
		Core_Manager::get_instance()->flush();
	}
}
```

> **Рекурсивное удаление**: при рекурсивном удалении дочерних сущностей (аргумент `$is_recursion = true`) событие `cpm_core_entity_delete` **не** вызывается на вложенных шагах рекурсии: уведомление об удалении подписчики получают только для корневой сущности. Это избавляет расширения от лишних срабатываний при каскадном удалении (например, при удалении проекта удаляются его списки, задачи и вехи без отдельных событий).

## Подписка на события

Пример подписки расширения на создание задачи:

```php
add_action( 'cpm_core_entity_create_task', function( $task ) {
	// Отправка уведомления о новой задаче
	// $task — объект задачи, обёрнутый декоратором
} );
```

Пример подписки на удаление любой сущности:

```php
add_action( 'cpm_core_entity_delete', function( $entity ) {
	// Логирование удаления
} );
```

## Зачем передавать объект, а не id

- Подписчику не нужно заново выполнять запрос к БД.
- Объект уже обёрнут декоратором, поэтому подписчик работает с защищённым правами интерфейсом и не повторяет проверки прав.
- В свойствах объекта доступны `id`, `title`, `content`, `parent`, `author`, `get_project()` и т.п., что покрывает большинство сценариев уведомлений.

## Связанные документы

- `entity.md` — место встраивания хуков (`save()`, `delete()`).
- `core-manager.md` — фабричный метод `load_list()`, будущее место события чтения (если понадобится).
- `activity.md` — потребитель событий для ведения журнала действий.
