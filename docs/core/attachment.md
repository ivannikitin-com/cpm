# Класс Attachment

Класс сущности «Файл вложения» (`\CPM\v3\Core\Attachment`). Отражает файл, прикреплённый к комментарию или сущности CPM. Наследует `Project_Entity`.

> **Статус**: архитектура согласована (хранение в приватной подпапке `uploads/cpm/`, доступ через REST, обратная совместимость со старыми вложениями). Детали реализации (SQL, точный набор полей, REST-маршруты) требуют доработки на этапе кода. См. `открытые-вопросы.md`.

## Назначение и граница ответственности

> Ядро = хранение и доступ, UI = отображение.
> В ядре `Attachment` отвечает **только за хранение вложения и доступ к нему** (загрузка, привязка к проекту/комментарию, проверка прав, URL). Отображение (миниатюры, превью, иконки типов) реализуется **отдельным классом в модуле UI**, который принимает объект `Attachment` и выводит его. Ядро не занимается рендерингом.

## Связь с проектом

`Attachment` наследует от `Project_Entity` и всегда принадлежит проекту. Привязка к проекту хранится в мета-поле `_project` на самом вложении. `get_project()` возвращается через это значение.

## Права доступа

| Роль | Право |
| ---- | ----- |
| MANAGER | modify_own |
| CO_WORKER | modify_own |
| CLIENT | no_access |
| ADMINISTRATOR | полный доступ |

Декоратор: `Stuff_Decorator` — доступ только для сотрудников (роли `MANAGER`/`CO_WORKER`), модификация только своих вложений; для `CLIENT` доступ запрещён.

## Хранение: приватная папка `uploads/cpm/`

**Решение.** Файлы CPM хранятся в **отдельной приватной подпапке** `uploads/cpm/`, а не в общей `uploads/`. Это решает проблему приватности: файлы, прикреплённые к комментариям, могут быть конфиденциальными и не должны быть открыты по прямой ссылке.

### Почему отдельная подпапка

- Общая папка `uploads/` доступна из интернета — любой, кто знает URL, скачает файл без проверки прав CPM.
- Полная блокировка `uploads/` невозможна: она сломает остальные медиа сайта (не-CPM).
- Отдельная подпапка `uploads/cpm/` закрывается целиком правилами сервера (`.htaccess` / nginx), не затрагивая остальные загрузки.

### Прямой доступ блокируется

На подпапку `uploads/cpm/` накладывается запрет прямого доступа (HTTP-конфиг). Файл доступен только через прокси-эндпоинт (см. ниже), который проверяет права.

## Доступ: через REST-прокси

**Решение.** Файлы отдаются через **REST-эндпоинт**, а не по прямой ссылке. UI активно использует REST API, поэтому REST достаточно и для встраивания картинок (`<img src="/wp-json/cpm/v1/attachment/{id}">`), и для скачивания.

Схема:

- `GET /wp-json/cpm/v1/attachment/{id}` — отдаёт содержимое файла (бинарные данные) с корректным `Content-Type` и заголовками.
- Эндпоинт проверяет права через `ACL::get_role()` на проект вложения; при отсутствии доступа — `403 Forbidden`.

Это даёт контроль доступа к каждому файлу, единую точку для кэширования и логирования, возможность встраивать картинки и скачивать файлы.

## Свойства

`Attachment` заполняет свойства при чтении из метаданных WordPress, чтобы UI не пересчитывал тип и размеры при каждом рендере.

| Свойство | Тип | Назначение | Источник |
| -------- | --- | ---------- | -------- |
| `id` | int | ID вложения | `post.ID` |
| `parent` | int | Сущность, к которой прикреплён файл | `post_parent` |
| `author` | int | Автор (загрузивший файл) | `post_author` |
| `title` | string | Имя файла (без расширения) | `post_title` |
| `created_at` | string | Дата загрузки | `post_date` |
| `mime_type` | string | MIME-тип (например, `application/pdf`) | `post_mime_type` |
| `is_image` | bool | Является ли вложение картинкой | `wp_attachment_is_image()` |
| `width` / `height` | int | Размеры (для изображений) | `_wp_attachment_metadata` |
| `size` | int | Размер файла в байтах | `_wp_attachment_metadata` / filesize |

## Методы

- `get_project()` — возвращает проект вложения через `_project`.
- `get_url($size = null)` — URL содержимого через REST-прокси (приватный доступ). Для картинок `$size` можно передать размер миниатюры.
- `get_thumbnail_url()` — URL миниатюры (для изображений).
- `get_icon()` — идентификатор иконки типа (PDF, Word, изображение и т.п.). Использует `wp_mime_type_icon()` / кастомные иконки CPM. Возвращает идентификатор/URL иконки; рендер — в UI.
- `get_download_url()` — URL для скачивания с проверкой прав.
- `save()` / `delete_entity()` — загрузка и удаление файла. `delete_entity()` дополнительно удаляет физический файл из `uploads/cpm/` через `wp_delete_attachment()`.

## Привязка вложения

Связь вложения с сущностями хранится на двух уровнях (один источник истины на каждом):

| Связь | Хранение | Назначение |
| ----- | -------- | ---------- |
| Вложение → проект | мета `_project` на вложении | проверка прав, выборка файлов проекта |
| Вложение → комментарий | `commentmeta._files` (сериализованный массив ID) | отображение файлов комментария |

> **Чем не является связь**: `post_parent` вложения **не используется** как связь с комментарием — это служебное поле. Основная привязка файла к комментарию — через `commentmeta._files`. Такая схема исключает тройное дублирование связи (в старом коде были одновременно `_files`, `post_parent` и `_project`).

## Обратная совместимость

**Решение.** Старые вложения (27 238 записей `attachment`, из них 24 362 с мета `_project`) **не мигрируются и не перемещаются**. Новый класс читает их штатно:

- связь с комментарием — из существующего `commentmeta._files`;
- привязка к проекту — из существующего мета `_project`;
- тип/размер — из стандартных метаданных WordPress.

Новые файлы загружаются в `uploads/cpm/`. Старые файлы, лежащие в общей `uploads/`, продолжают отдаваться через тот же REST-прокси (прокси читает путь из метаданных и отдаёт файл вне зависимости от фактического расположения). Это обеспечивает бесшовный переход: старые и новые вложения работают одинаково через REST.

## Права на вложение (для прокси)

При отдаче файла через REST-прокси проверяется доступ текущего пользователя к проекту вложения:

- `ACL::get_role()` на проект → `CLIENT` имеет `no_access` к вложениям, поэтому для `CLIENT` возвращается `403`.
- Сотрудники (`MANAGER`/`CO_WORKER`) и администратор получают файл.

## Загрузка файла (v3, решение)

Загрузка выполняется в ядре класса `Attachment` (вызывается REST-контроллером после получения multipart):

- `Attachment::validate_upload($file)` — чистая валидация элемента `$_FILES`: файл передан и без ошибки, размер в пределах `cpm_max_upload_size` (по умолчанию лимит WordPress `wp_max_upload_size()`), тип — по whitelist `cpm_allowed_mime_types` (по умолчанию документы/картинки/архивы). Возвращает `true` или `WP_Error`.
- `Attachment::create_from_upload($file, $project_id, $parent)` — валидация, сохранение файла в приватную подпапку `uploads/cpm/` (через `wp_handle_upload()` с фильтром `upload_dir`), создание записи `attachment` (`wp_insert_attachment()`), генерация метаданных, запись мета `_project`/`_parent`. Если `parent` — комментарий, ID вложения добавляется в `commentmeta._files` комментария (`bind_to_comment()`).

> Права на создание вложения проверяет вызывающий слой (REST через декораторы/ACL), а не `create_from_upload()`.
