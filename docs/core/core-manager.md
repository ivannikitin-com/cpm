# Класс Core_Manager

Основной класс ядра (`\CPM\v3\Core\Core_Manager`). Реализован как **синглтон** — доступ из любого места кода:

```php
$object = \CPM\v3\Core\Core_Manager::get_instance()->create( ... );
```

## Функции

- Загружает все файлы классов ядра при инициализации через `require()` (никаких автозагрузчиков). Все файлы и классы ядра всегда загружены.
- Регистрирует Custom Post Types последовательным вызовом.
- Создаёт экземпляры сервисных классов, чтобы предоставить доступ к:
  - спискам проверки доступа — класс `ACL`;
- Предоставляет фабричный метод `load_list($type, $args)` — загружает из БД и возвращает массив объектов, обёрнутых декоратором.
- Предоставляет фабричный метод `create($type, $args)` — создаёт в БД и возвращает объект сущности, обёрнутый декоратором.

## Структура

| Член | Тип | Назначение |
| ---- | --- | ---------- |
| `instance` | Core_Manager (static, private) | Экземпляр класса |
| `acl` | ACL | Проверки доступа |
| `get_instance()` | static : Core_Manager | Возврат экземпляра |
| `load_list($type, $args)` | Entity[] | Выборка списка сущностей (с пагинацией/сортировкой) |
| `count_list($type, $args)` | int | Общее число сущностей по фильтрам (для заголовков пагинации) |
| `create($type, $args)` | Entity | Создание сущности |
| `flush()` | void | Сброс кэшей (своих и ACL) |

## Методы

### `load_list($type, $args)` — выборка сущностей

Фабричный метод выполняет выборку данных из БД и формирует массив объектов сущностей, обёрнутых декоратором.

**Важно**: метод `load_list()` **не использует** `WP_Query` или типовые подходы WordPress для выборки CPT и мета-данных. Требование — максимально сократить число SQL-запросов. Предыдущая версия CPM выполняла 400–500 запросов при инициализации и выборке списка проектов. Выборка списка сущностей должна выполняться буквально **одним запросом**.

Каждый класс сущности содержит статические свойства-константы:

- `CPT` — тип записей WordPress (Custom Post Type), например `cpm_project`;
- `SQL` — SQL-запрос выборки записей этого типа со всеми полями и фильтрами.

#### Пагинация и сортировка (решение)

`load_list()` принимает аргументы пагинации и сортировки (нужны REST API, решения №14–15):

| Аргумент | Тип | Назначение |
| -------- | --- | ---------- |
| `page` | int ≥ 1 | Номер страницы |
| `per_page` | int ≥ 1 | Размер страницы (LIMIT) |
| `offset` | int ≥ 0 | Сдвиг от начала (приоритетнее `page`) |
| `orderby` | string | Колонка сортировки — **только из белого списка** для типа сущности (см. ниже) |
| `order` | string | `asc` / `desc` (по умолчанию `asc`) |

- Пагинация применяется только если задан `per_page` (или `page`). `offset` вычисляется как `(page-1) * per_page`, либо берётся из явного `offset`.
- Сортировка по произвольному `orderby` **не подставляется в SQL**: значение сверяется с белым списком колонок типа (`Core_Manager::$orderable`) и отбрасывается при несовпадении — защита от SQL-инъекций.
- Пагинация/сортировка накладываются на выборку обёрткой `SELECT * FROM ( <sql> ) AS cpm_rows ...` — так как у разных сущностей разный состав колонок, сортировка по псевдониму колонки выполняется во внешнем запросе.
- Для сущностей на комментариях (`comment`, `activity`) пагинация/сортировка транслируются в аргументы `WP_Comment_Query` (`number`, `offset`, `orderby`, `order`) в их статических `query_rows()`.

**Общее число записей** (для заголовков пагинации `X-WP-Total*`) возвращает метод `count_list($type, $args)`: он считает строки с теми же фильтрами, игнорируя `page`/`per_page`/`offset`/`orderby`/`order`. Для `comment`/`activity` счёт выполняется через `query_count()` (тот же `WP_Comment_Query` с `count => true`).

#### Сопоставление типа сущности и класса (маппинг «тип → SQL»)

`load_list()` получает первым аргументом строковый тип сущности (`'project'`, `'task'`, `'task_list'` и т.д.) и по нему находит класс сущности и его SQL-запрос. Строковый тип возвращает метод `get_type()` у сущности (нижний регистр, без префикса пространства имён) — он используется как ключ.

Маппинг хранится в `Core_Manager` как статический массив:

```php
private static $entity_types = array(
	'project'   => 'Project',
	'task_list' => 'Task_List',
	'task'      => 'Task',
	'message'   => 'Message',
	'milestone' => 'Milestone',
	'note'      => 'Note',
	// ...
);
```

#### Алгоритм `load_list($type, $args)`

1. По `$type` находится класс сущности `$class` из `$entity_types`.
2. Берётся статичное свойство `$class::SQL` — готовый запрос выборки.
3. В запрос подставляются фильтры из `$args` (параметризованно через `$wpdb->prepare()`), в т.ч. фильтр по текущему пользователю (для `administrator` — без фильтра по участнику).
4. Запрос выполняется `$wpdb->get_results()`; каждая строка превращается в объект сущности `$class` (данные из SQL напрямую, повторных запросов нет).
5. Каждый объект оборачивается декоратором и добавляется в возвращаемый массив.

Для получения единичного объекта используется запрос с `$args = array( 'id' => 123 )`. Но `load_list()` **всегда возвращает массив**, даже если в нём один элемент.

### Выбор декоратора для сущности

При оборачивании объекта сущности декоратор выбирается по **роли текущего пользователя** и **типу сущности** на основе таблицы прав (`права-и-роли.md`).

Порядок выбора:

1. Роль текущего пользователя определяется через `ACL::get_role( $entity )`.
2. Если роль `ADMINISTRATOR` — сущность не ограничивается (`Modify_Decorator` либо декоратор не применяется).
3. Если роль `NO_ROLE` — сущность недоступна для модификации (`ReadOnly_Decorator` или сущность исключается из выборки).
4. Иначе по паре «тип сущности → роль» выбирается декоратор из таблицы прав.

> Нормативная таблица прав находится в `docs/core/права-и-роли.md`. При расхождении с примерами в этой спецификации действует нормативная таблица (Project для MANAGER = `modify*`, декоратор `Modify_Decorator`).

Если конкретный декоратор не реализует ограничения для пары «тип × роль», он делегирует проверку базовому `Base_Decorator`.

### `create($type, $args)` — создание сущности

Фабричный метод создаёт новую сущность, записывает её в БД и возвращает объект, обёрнутый декоратором.

Алгоритм:

1. По `$type` находится класс сущности `$class` (как в `load_list()`).
2. Создаётся новый объект `$class`, свойства заполняются из `$args`.
3. Вызывается `save()`: для новой записи (`$this->id === 0`) выполняется `wp_insert_post()`, объекту присваивается новый `id`.
4. После сохранения вызывается `flush()` у `Core_Manager`, чтобы сбросить кэши ACL.
5. Объект оборачивается декоратором по тем же правилам, что и в `load_list()`, и возвращается.

> Проверка прав: перед созданием сущности права текущего пользователя на `modify` данного типа сущности должны быть проверены (через `ACL::get_role()` и таблицу прав). Попытка создания запрещённого типа сущности (например, вехи пользователем с ролью `CLIENT`) должна приводить к отказу.

### `flush()`

Сбрасывает свои кэши и вызывает `flush()` у класса `ACL`. Вызывается после изменения данных (подробнее — `кэширование.md`).
