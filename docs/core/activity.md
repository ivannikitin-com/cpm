# Класс Activity

Класс сущности «Активность» (`\CPM\v3\Core\Activity`). Отражает запись журнала действий (ленту активности) в проекте CPM. Это сообщения вида «Задача *Настроить отправку форм CF7* закрыта пользователем *Иван Никитин*», «*Надежда Афоничева* оставил(а) комментарий в *Доработки сайта*».

> **Статус**: механика подтверждена по реальной БД и коду старой версии CPM (`wedevs-project-manager-pro`). Детали реализации v3 (SQL, точный набор свойств) требуют доработки. См. `открытые-вопросы.md`.

## Главное: как активность хранится в старой версии

Активность CPM **не является Custom Post Type**. В старой версии это **комментарии WordPress** (таблица `comments`) с типом `comment_type = 'cpm_activity'`. Подтверждено реальной БД:

- В таблице `comments` 234 947 записей с `comment_type = 'cpm_activity'`.
- Каждая запись привязана к `comment_post_ID` (сущности, к которой относится действие: проект, задача, список задач и т.п.).
- `user_id` — пользователь, выполнивший действие.

> **Важно**: сущность `activity` (22 585 записей в `posts`) — это CPT **другого плагина** (WeDevs Project Manager), к ядру CPM v3 она отношения не имеет. Её не трогаем. Лог CPM v3 — это комментарии типа `cpm_activity`, а не CPT.

## Механизм создания: связка с событиями (хуками)

Старая версия **уже использовала хуки** для создания активности. Класс `CPM_Activity` подписывался на события CPM и на каждое действие записывал комментарий типа `cpm_activity`:

```php
add_action( 'cpm_project_new', array( $this, 'project_new' ) );
add_action( 'cpm_task_done',   array( $this, 'task_done' ) );
add_action( 'cpm_comment_new', array( $this, 'comment_new' ), 10, 2 );
add_action( 'cpm_task_new',    array( $this, 'task_new' ), 10, 2 );
// ... и т.д.
```

Каждый обработчик формировал текстовое сообщение и записывал его методом `log()`:

```php
function log( $post_id, $message ) {
	$commentdata = array(
		'comment_type'    => 'cpm_activity',
		'comment_content' => $message,   // обычный текст
		'comment_post_ID' => $post_id,   // сущность, к которой относится действие
		'user_id'         => $user->ID,
		// ...
	);
	wp_insert_comment( $commentdata );
}
```

Это в точности та модель, что предлагалась для v3: **активность — идеальный потребитель хуков**. В v3 она подписывается на события `cpm_core_entity_*` (см. `хуки-события.md`).

> **Решение: в v3 шорткоды в логах НЕ реализуются.** Легаси-подход со шорткодами (`[cpm_task_url ...]` и т.п.) в v3 **отбрасывается**. Причины:
> - Лог должен быть читаемым **без доп. обработки** — это его назначение. Шорткоды в сырой БД нечитаемы.
> - Логи смотрят редко, сложность рендеринга не окупается.
> - Нет зависимости от живых объектов: при удалении задачи шорткод становится битым, а простой текст всегда самодостаточен.
>
> В v3 активность пишет **обычный человекочитаемый текст**: «Задача "Настроить отправку форм CF7" закрыта пользователем Иван Никитин».

### Пример формирования сообщения (v3)

```php
// v3: запись лога по событию завершения задачи
$message = sprintf(
	'Задача "%s" закрыта пользователем %s',
	$task->title,
	wp_get_current_user()->display_name
);
$this->log( $task->get_project()->id, $message );
```

Название сущности фиксируется **на момент действия**. Для лога это корректнее: запись фиксирует факт «как было тогда».

## Чтение лога

Лог читается штатными функциями WordPress для комментариев, с фильтром по `comment_type`:

```php
function get_activity( $project_id, $args = array() ) {
	$args['post_id'] = $project_id;
	$response = get_comments( apply_filters( 'cpm_activity_args', $args, $project_id ) );
	return $response;
}
```

Фильтр `cpm_activity_args` позволяет ограничить выборку именно записями `comment_type = 'cpm_activity'` и исключить реальные комментарии. Сортировка обычно `DESC` (новые сверху), ограничение `number` (например, 20).

### Чтение лога в v3 (решение по SQL и фильтрам)

**Решение.** В v3 запись лога всегда пишется **на проект**: `comment_post_ID` записи `cpm_activity` равен ID проекта (`$this->log( $task->get_project()->id, $message )`, см. пример выше). Поэтому чтение лога проекта — это фильтр по проекту и типу комментария, без обхода поддерева сущностей.

Чтение лога выполняется фабрикой ядра через `load_list( 'activity', $args )` так же, как для остальных сущностей:

| Аргумент `load_list()` | Назначение |
| ---------------------- | ---------- |
| `project_id` | Лог указанного проекта (`comment_post_ID` = проект). Основной фильтр списка |
| `id` | Единичная запись лога (массив из 0/1) |
| `parent` | Записи старой версии, привязанные к конкретной сущности (см. ниже) |

Сортировка — `comment_date DESC` (новые сверху), поддерживается пагинация (`page`/`per_page`/`offset`), общий подсчёт для заголовков `X-WP-Total*` (REST API). Права соблюдаются на уровне выборки: запрос возвращает только лог проектов, доступных текущему пользователю (фильтр `is_admin OR team LIKE ...`), — см. прототип SQL ниже.

> **Старые записи.** Записи лога, созданные старой версией и привязанные к сущности проекта (`parent` = сущность, не проект), в список лога **проекта** по фильтру `project_id` не попадают — они читаются как лог соответствующей сущности через `parent`. Массовая конвертация не выполняется (`docs/совместимость.md`, решение «Старые записи лога Activity не мигрируются»). Если на практике понадобится читать их в логе проекта, пишется разовый запрос по требованию.

SQL-прототип списка лога проекта (реальные имена таблиц и `prepare()` — в продакшн-коде):

```sql
--
-- Лента активности проекта CPM v3
--
SELECT
	c.comment_ID AS id,
	c.comment_content AS content,
	c.user_id AS author,
	c.comment_date AS created_at,
	c.comment_post_ID AS parent
FROM
	in_comments c
		INNER JOIN in_posts p
			ON p.ID = c.comment_post_ID
		INNER JOIN in_postmeta pm
			ON pm.post_id = p.ID AND pm.meta_key = '_team'
WHERE
	c.comment_type = 'cpm_activity'
	AND p.post_type = 'cpm_project'
	AND ( is_admin OR pm.meta_value LIKE '%"277"%' ) -- участник проекта (ID текущего пользователя)
	AND c.comment_post_ID = %d                         -- project_id
ORDER BY
	c.comment_date DESC
```

> **Прототип SQL.** В реальном коде — параметризованный запрос `$wpdb->prepare()`, имена таблиц `$wpdb->comments`, `$wpdb->posts`, `$wpdb->postmeta`. Условие `is_admin OR team LIKE ...` формируется динамически (как в `выборка-sql.md`). Учёт старой схемы участников (`in_cpm_user_role`) — через `COALESCE()`, как в `чтение-участников-sql.md`.

## Связь с проектом и права

`Activity` принадлежит проекту: `comment_post_ID` указывает на сущность проекта, от которой через цепочку получается проект (`get_project()` через `Project_Entity`). Права на чтение лога определяются доступом к проекту.

## Свойства

Поскольку активность — это комментарий, свойства наследуют поля таблицы `comments`:

| Поле | Назначение |
| ---- | ---------- |
| `id` | `comment_ID` |
| `content` | `comment_content` — человекочитаемый текст действия |
| `author` | `user_id` — пользователь, выполнивший действие |
| `created_at` | `comment_date` — дата/время действия |
| `parent` | `comment_post_ID` — сущность, к которой относится действие |

## Реализация в v3

В v3 `Activity` следует реализовать как отдельный класс, наследующий `IEntity`/`Entity`, но работающий с таблицей `comments` (как `Comment`), а не с CPT. Он:

- хранит содержимое как **обычный текст** (без шорткодов, см. `контент-сущностей.md`);
- создаётся автоматически при срабатывании хуков `cpm_core_entity_*`;
- доступен только для чтения (декоратор `ReadOnly_Decorator`), без возможности изменять.

## Обратная совместимость (решение)

Старые записи лога (234 947 комментариев `cpm_activity`) **не мигрируются и не преобразуются**. Они содержат шорткоды (`[cpm_task_url ...]`, `[cpm_user_url ...]` и т.п.), но трогать их не требуется:

- Логи смотрят редко, поэтому нецелесообразно конвертировать ~250K записей.
- При чтении старые записи **выводятся как есть** — необработанные шорткоды.
- Если в будущем понадобится расшифровать старые логи, пишется разовый скрипт по требованию (не является частью ядра).

Новые записи (создаваемые в v3) пишутся обычным текстом, поэтому эта проблема их не касается.
