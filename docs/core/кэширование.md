# Стратегия кэширования CPM

Кэширование нужно для снижения нагрузки на БД: при выборке списков и рекурсивном удалении сущностей проверки прав требуют обращения к участникам проектов. Кэш избегает повторных запросов.

> Статус в источниках: «Проект (требует подтверждения)», но ключевые решения приняты и зафиксированы ниже.

## Что кэшируется

| Данные | Где создаётся | Ключ | Комментарий |
| ------ | ------------- | ---- | ----------- |
| Список ID проектов для пользователя | `ACL::get_user_projects($user_id)` | `cpm_acl_user_{user_id}` | Основа проверки прав |
| Объект проекта (по `project_id`) | `Core_Manager` / `get_project()` | `cpm_project_{id}` | Создаётся по требованию из `project_id` |
| Выбранные списки сущностей | `Core_Manager::load_list()` | зависит от `$type` и `$args` | Опционально (по умолчанию не кэшируется) |

Роль конкретного пользователя для сущности вычисляется из кэшированного объекта проекта, поэтому отдельно роль не кэшируется — она дёшево получается из `$project->team->members`.

## Механизм

Рекомендуется использовать **WordPress Object Cache** (`wp_cache_get()` / `wp_cache_set()`). Причины:

- Объектный кэш действует в рамках запроса и всегда консистентен — после изменения данных сброс в рамках того же запроса гарантирован.
- Не требует настройки внешнего кэша (memcached/Redis) и работает без него.
- Данные CPM меняются часто, поэтому постоянный (межзапросный) кэш потребовал бы тщательной инвалидации и рискует выдавать устаревшие права.

## Ключи и пространство имён

Все ключи имеют префикс `cpm_` (уже заложен в существующих данных). Примеры:

- `cpm_acl_user_{user_id}` — доступные пользователю проекты.
- `cpm_project_{id}` — объект проекта.
- `cpm_list_{type}_{hash(args)}` — список сущностей (если включено).

Хэш аргументов в ключе списка нужен, чтобы разные фильтры не пересекались.

## Сброс кэша (инвалидация)

`Core_Manager::flush()` сбрасывает кэш `Core_Manager` и вызывает `ACL::flush()`. Вызывается после изменения данных:

| Событие | Кто вызывает flush |
| ------- | ------------------ |
| `save()` сущности | `Entity` (после `wp_update_post()` / `wp_insert_post()`) |
| `create()` | `Core_Manager` |
| `delete()` не в рекурсии | `Entity` |
| `delete()` в рекурсии | отложенно |

### Отложенный сброс при рекурсивном удалении

При рекурсивном удалении (`Entity::delete($is_recursion)`) кэши **не сбрасываются** на каждом вложенном шаге, а только после завершения всей рекурсии:

```php
if ( ! $is_recursion ) {
	Core_Manager::get_instance()->flush();
}
```

Это снижает число сбросов и запросов при удалении поддерева сущностей.

### Сброс при изменении участников

При изменении `Team` проекта (добавление/удаление участников) необходимо сбросить `cpm_acl_user_{user_id}` для затронутых пользователей, чтобы обновить их список доступных проектов.

## Инвалидация — целиком или точечно

Простейший и надёжный вариант — **сбрасывать весь кэш CPM** (`flush()`) при любом изменении данных. Нагрузка от этого невелика, поскольку объём кэша ограничен текущим запросом.

## Что НЕ кэшируется

Списки сущностей по умолчанию не кэшируются: выборка — один параметризованный запрос, дополнительные запросы кэш не экономит. Кэш списков включается только при явной необходимости.

## Принятые решения по кэшу

### Объектный кэш vs transients

**Используется только WordPress Object Cache** — кэш в рамках текущего запроса. Transients (`set_transient()`/`get_transient()`) для кэширования прав **не используются**. Причины:

- **Кэш прав — это вопрос безопасности.** Устаревшие права (пользователь остался в проекте после удаления из команды или, наоборот, потерял доступ) — это ошибка прав доступа. Консистентность в рамках запроса гарантирована, так как после изменения данных `flush()` сбрасывает кэш в том же запросе.
- **Transients пришлось бы инвалидировать точечно**, а CPM меняет участников проектов часто. Риск устаревшего кэша прав перевешивает выигрыш в скорости.
- Список ID проектов пользователя (`cpm_acl_user_*`) вычисляется одним параметризованным запросом, а не дорогой операцией.
- **Исключение**: если будущий профилинг покажет, что выборка `cpm_acl_user_*` является узким местом, допустимо ввести transient, но тогда обязательна инвалидация по ключу при изменении участников. На этапе проектирования этого не делаем.

### Кэширование списков сущностей

**По умолчанию не включается.** Выборка списка — один параметризованный SQL-запрос, который уже оптимизирован. Кэширование списков (`cpm_list_...`) добавило бы сложность без существенной экономии. Включается только при явной необходимости, зафиксированной по результатам замеров.

### Инвалидация при изменении участников

**По умолчанию сбрасывается весь кэш CPM** (`flush()`), что покрывает и списки, и `cpm_acl_user_*`. Это надёжно и просто, так как объём кэша ограничен текущим запросом.

Точечная инвалидация применяется как **оптимизация**, если будут введены transients или если понадобится снизить число сбросов при массовых операциях с участниками.
