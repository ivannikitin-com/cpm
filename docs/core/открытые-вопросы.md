# Открытые вопросы и принятые решения

Единый реестр открытых вопросов и зафиксированных решений по ядру CPM v3. Агент должен проверять этот документ перед реализацией соответствующего модуля.

## Принятые решения (зафиксировано)

| № | Тема | Решение |
| -- | ---- | ------- |
| 1 | Модель запрета в декораторах | Ядро выбрасывает `AccessDeniedException`; обработка — в UI/REST (`ошибки.md`) |
| 2 | Transients для прав | **Не используются** для кэша прав; только WordPress Object Cache (`кэширование.md`) |
| 3 | Кэширование списков сущностей | По умолчанию **не включается** (`кэширование.md`) |
| 4 | Инвалидация при изменении участников | По умолчанию — весь кэш CPM через `flush()`; точечно — как оптимизация |
| 5 | Шорткоды в логах Activity | В v3 **отбрасываются**; пишется обычный человекочитаемый текст (`activity.md`) |
| 6 | Миграция старых данных | Отдельный скрипт миграции **не создаётся**; бесшовный переход моделью чтения/записи (`совместимость.md`) |
| 7 | Хранение файлов CPM | Приватная подпапка `uploads/cpm/`, доступ через REST-прокси (`attachment.md`) |
| 8 | Миграция старых вложений | Старые вложения **не мигрируются и не перемещаются**, читаются штатно через REST-прокси (`attachment.md`) |
| 9 | Старые записи лога Activity | **Не мигрируются**, выводятся как есть (`activity.md`) |
| 10 | Иерархия задач | Подзадачи в v3 не используются; чтение старых данных обрабатывает parent = список/проект/задача (`task.md`) |
| 11 | Базовый декоратор | Актуальная модель — `can_modify()` + `AccessDeniedException`; старая модель `prepare()/check_save()/check_delete()` — устаревшая (`base-decorator.md`) |
| 12 | Таблица прав | Нормативная таблица — в `права-и-роли.md` (Project для MANAGER = `modify*`, `Modify_Decorator`) |
| 13 | `PermissionsChecker` (устаревший) | Заменён на связку `ACL` + декораторы. Идея «цепочки участников» (свои → родитель → проект) заменена моделью «права только на уровне проекта» (`Project_Entity`) |

## Открытые вопросы (требуют решения)

### Ядро — общее

- [ ] **Task: редкие случаи иерархии в запросе списка.** SQL-запрос списка задач строится из предположения `parent` = список задач. Случаи `parent` = проект или = задача в запросе списка не покрыты. Решение принято только для чтения единичной задачи. Как вести себя при выборке списком (исключать / подтягивать через цепочку / не поддерживать)? (`task.md`)

### Сущности

- [x] **Comment**: набор свойств и чтение через ядро — **решено** (`comment.md`: поля ↔ `comments`, `query_rows()`/`query_count()`). Осталась обратная совместимость чтения старых записей.
- [x] **Attachment**: SQL-выборка, загрузка (multipart, whitelist, размер), привязки `_parent`/`commentmeta._files` — **решено** (`attachment.md`). Осталась логика иконок типов.
- [x] **Activity**: точный набор хуков — **решено** (лог по всем мутациям сущностей проекта, кроме activity и без проекта; `activity.md`). SQL-запрос выборки лога — **решён** (`activity.md`).

### Контент

- [ ] **Где преобразовывать старые форматы контента**: в `get_wp_args()` при сохранении (ядро) или при чтении (UI)? По умолчанию предполагается `get_wp_args()` в `Entity`. (`контент-сущностей.md`)
- [ ] **Определение формата строки контента**: как UI определяет, что строка — Markdown/HTML/шорткод, и где выполняется парсинг. (`контент-сущностей.md`)
