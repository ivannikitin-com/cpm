# Роли и права на сущности ядра (нормативный справочник)

**Нормативный справочник**: таблица прав для каждого типа сущности, маппинг «роль → декоратор», формат хранения участников (`_team`) и логика обратной совместимости. **Именно этот документ является источником истины для выбора декоратора в `Core_Manager`.**

Смысл и историю самих ролей (что может manager / co_worker / client) см. в `семантика-ролей.md`.

Решение о том, как сохранять и обрабатывать данные о пользователях отдельной сущности, нестандартное и является компромиссом между простотой, логичностью и числом запросов в БД при чтении списка сущностей. В силу необходимости реализации режима совместимости SQL-запросы и способы реализации могут казаться нетиповыми. Следует жёстко придерживаться принципов, описанных в документации, и не пытаться это улучшить.

## Роли пользователей

Роли определены как константы в классе `ACL`:

- `ADMINISTRATOR`
- `MANAGER`
- `CO_WORKER`
- `CLIENT`
- `NO_ROLE`

Роль пользователя возвращается методом `get_role($entity, $user_id)` класса ACL.

## Виды прав

| Право | Описание |
| ----- | -------- |
| `read` | Разрешено чтение элементов, входящих в проект, к которому у пользователя есть доступ (реализуется `Core_Manager`) |
| `modify` | Разрешена модификация (создание, сохранение, удаление) |
| `modify_own` | Разрешена модификация только своих объектов (автор сущности — указанный пользователь) |
| `no_access` | Доступ запрещён (реализуется `Core_Manager`) |

## Декораторы и права на изменения сущностей

| Сущность | MANAGER | CO_WORKER | CLIENT | Декоратор |
| -------- | ------- | --------- | ------ | --------- |
| Project | modify* | read | read | `Modify_Decorator` |
| Task_List | read | read | read | `ReadOnly_Decorator` |
| Task | modify | modify_own | modify_own | `Modify_Decorator` |
| Comment | modify_own | modify_own | modify_own | `ModifyOwn_Decorator` |
| Message | modify_own | modify_own | modify_own | `ModifyOwn_Decorator` |
| Milestone | modify_own | modify_own | no_access | `Stuff_Decorator` |
| Attachment | modify_own | modify_own | no_access | `Stuff_Decorator` |
| Activity | read | read | no_access | `ReadOnly_Decorator` |

- Роль `ADMINISTRATOR` имеет доступ ко всем сущностям и может модифицировать любые сущности.
- Роль `NO_ROLE` не имеет доступа ни к чему и не может менять ничего.

> **Звёздочка `modify*` у Project**: `manager` может всё в проекте (редактировать, архивировать, переводить в выполненное состояние, менять координатора и участников), **кроме удаления самого проекта**. Удаление проекта — прерогатива только роли `ADMINISTRATOR`.
>
> Эта особенность реализуется не декоратором (декоратор `Modify_Decorator` разрешает полную модификацию), а отдельной проверкой в `delete()` проекта. См. `project.md`.

> **Расхождение в источниках**: в одном из документов (`core-manager.md` в Obsidian) для Project у `MANAGER` указано `read` и декоратор `ReadOnly_Decorator`. Это устаревшая версия таблицы. **Действует нормативная таблица выше**: Project для `MANAGER` — `modify*` (`Modify_Decorator`).

## Хранение ролей в БД

### Старая версия

В старых версиях CPM роли хранятся в отдельной таблице `in_cpm_user_role` (префикс `in_` может быть любым):

```
in_cpm_user_role {
	int    ID           PK  "ID записи"
	int    project_id       "ID проекта"
	int    user_id          "ID пользователя"
	string role             "Роль пользователя"
	string component        "Не используется"
}
```

### Новая версия (v3)

Роли и пользователи хранятся в метаданных поста с ключом `_team` в виде строки `"user_id":role, ...`, например:

```
"12":manager,"15":co_worker,"22":co_worker,"33":client
```

`user_id` — целое число, но сохраняется как строка в двойных кавычках, чтобы явно избежать ошибок сопоставления значений (например, `12` является частью `112`, но это разные значения).

Такой формат строки требует дополнительной обработки, но при необходимости позволяет выполнять фильтрацию сущностей на уровне SQL-запроса:

```sql
WHERE _team LIKE '%"15"%'
```

Роль `ADMINISTRATOR` не сохраняется в БД, а определяется по роли WordPress текущего пользователя. Роль `NO_ROLE` предполагает отсутствие записей в БД и тоже не сохраняется.

### Чтение списка пользователей для сущности из БД

Чтение осуществляется в фабричном методе `load_list()` `Core_Manager` прямым запросом в БД. Чтение должно предусматривать в запросе и старый метод хранения (для обратной совместимости), и новый. Если для сущности есть запись и в старом, и в новом формате, **приоритет отдаётся новому**. Это решается на уровне SQL-запроса для каждой сущности (через `COALESCE()`). См. `чтение-участников-sql.md`.

### Запись списка пользователей для сущности в БД

Запись значений ролей выполняется с помощью штатной функции WordPress при сохранении сущности. Запись списка пользователей всегда выполняется **только в новом формате** (`_team`).
