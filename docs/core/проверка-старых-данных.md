# Проверка чтения старых данных (2026-08-23)

Финальная проверка классов сущностей ядра на соответствие реальным данным БД `ivannikitin` (префикс `in_`). Цель — убедиться, что документированные SQL-запросы и поля корректно читают данные старой версии CPM.

## Подтверждённые форматы данных

### team (проекты) — таблица `in_cpm_user_role`

Формат `"user_id":role,...` формируется GROUP_CONCAT. Реальный пример (проект 6583):

```
"1":manager,"277":manager,"220":manager,"35":manager,...
```

`COALESCE()` в SQL-запросе корректно отдаёт приоритет новому формату `_team`, если он есть, иначе читает старую таблицу. У проектов в текущей БД `_team` отсутствует (все данные в старой таблице) — 2372 записи в `in_cpm_user_role`.

### team (задачи) — мета `_assigned`

`_assigned` хранит **несколько записей postmeta** на задачу (по одной на пользователя), а не сериализованную строку. SQL-запрос собирает их через `GROUP_CONCAT`:

```
"23":"","406":""
```

(задача 6936). Формат совпадает с документированным в `task.md`. `_team` у задач отсутствует.

### Comment — вложения

`commentmeta._files` — сериализованный массив ID вложений. **Важно:** у 132 527 из 150 563 комментариев мета `_files` = пустой массив `a:0:{}`. Только 18 036 содержат реальные файлы. Пустой `_files` — нормальное состояние, его следует обрабатывать как «файлов нет».

### Attachment

- Вложение = запись `attachment` (mime, title, status='inherit').
- Мета `_project` — ID проекта (24 362 из 27 238 вложений).
- Мета `_wp_attached_file` — путь файла.
- `post_parent` — сущность, но связь с конкретным комментарием только через `commentmeta._files`.
- Распределение mime: jpeg (10260), png (7301), docx (5648), xlsx (2289), pdf (529), zip (222) и др.

## Найденные расхождения / решения

### 1. Иерархия задач не плоская — решено

Распределение parent у задач (16 284 задач):

- `cpm_task_list` — 16 279;
- `cpm_project` — 3 (задача напрямую в проекте);
- `cpm_task` — 2 (вложенные подзадачи).

**Решение:** подзадачи в v3 не используются (редкие остатки ранних попыток), но чтение старых данных их обрабатывает. `parent` задачи может указывать на список задач, проект или другую задачу. Задокументировано в `task.md` и `entity.md`. `get_project()` вычисляет проект с учётом типа `parent`.

### 2. `_thumbnail_id` в старых данных отсутствует

У всех проверенных сущностей `_thumbnail_id` = NULL. Это ожидаемо (в старой версии картинок у сущностей не было), но значит: в v3 картинка появится только для новых записей. Чтение NULL должно корректно обрабатываться как «картинки нет».

### 3. Комментарии к нескольким типам сущностей

Комментарии привязаны не только к задачам (148 871), но и к `post` (3331), `cpm_message` (1029), `cpm_task_list` (644), `cpm_docs` (21). `get_project()` комментария должен уметь проходить цепочку для любого из этих типов.

## Вывод

Все классы сущностей корректно читают старые данные. Документированные форматы подтверждены реальной БД. Единственное существенное расхождение с документацией — **вложенная иерархия задач** (parent может быть задачей или проектом, а не только списком задач) — было решено и задокументировано в `task.md`.
