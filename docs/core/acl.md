# Класс ACL (Access Control List)

Класс `\CPM\v3\Core\ACL` хранит логику ролей пользователей для указанной сущности и вычисляет, к каким проектам у пользователя есть доступ. Класс **полностью статический** — нет нужды создавать его экземпляр.

## Константы класса

Константы являются **строковыми** (для обеспечения режима совместимости и упрощения выборки данных из таблиц БД):

| Константа | Значение |
| --------- | -------- |
| `ADMINISTRATOR` | `administrator` |
| `MANAGER` | `manager` |
| `CO_WORKER` | `co_worker` |
| `CLIENT` | `client` |
| `NO_ROLE` | `none` |

Везде используются именно константы, а не строковые значения:

```php
if ( ACL::MANAGER == $current_role ) ...
```

## Методы класса

| Метод | Назначение |
| ----- | ---------- |
| `get_role($entity, $user_id = wp_get_current_user()->ID)` | Возвращает роль для указанного пользователя (по умолчанию текущего) для указанной сущности. Для получения проекта вызывает `$entity->get_project()` |
| `get_user_projects($user_id)` | Возвращает массив ID проектов, к которым у пользователя есть доступ: `[11, 12, 15]` |
| `flush()` | Сбрасывает кэш вычисленных ID проектов для пользователей |

## Логика работы `get_role()`

Метод получает два параметра: сущность и ID пользователя для проверки.

1. Сначала проверяется, является ли `$user_id` администратором WordPress. Если да — сразу возвращается `ADMINISTRATOR`, дальнейшие действия не выполняются. Суть: администраторы могут всё.
2. Так как роли пользователя полностью определяются командой `Team` у проекта, вызывается `$entity->get_project()` для получения проекта.
   - Если метод вернул пусто (сущность не принадлежит проекту) — возвращается `NO_ROLE`.
   - Если вернул объект проекта — он сохраняется в переменную `$project`.
3. Проверяется массив `$project->team->members` и ищется роль для `$user_id`. Возвращается найденная роль или `NO_ROLE`.

## Логика и реализация `get_user_projects()`

Задача — получить массив ID проектов, к которым у указанного пользователя есть доступ. Списки пользователей в проектах для старой версии сильно отличаются:

- В старой версии роль пользователя хранится в отдельной таблице `in_cpm_user_role`.
- В новой версии роль пользователя хранится в мета-поле `_team`.

Метод должен учитывать, что если для некоего проекта указан и старый, и новый способ хранения, следует использовать данные **только нового** способа. Это позволяет перейти на новый способ для любого проекта, не модифицируя старую таблицу. Логика реализуется функцией `COALESCE()` в SQL-запросе: для любого проекта вычисляются две строки (по новому и по старому), но выбирается первая непустая.

```sql
--
-- Список проектов, к которым пользователь имеет доступ
--
SELECT
	ID AS id,
	COALESCE(
		-- Новая схема участников
		MAX(CASE WHEN pm.meta_key = '_team' THEN pm.meta_value ELSE NULL END),
		-- Старая схема участников
		(SELECT GROUP_CONCAT(CONCAT('"', user_id, '":', `role`)) FROM in_cpm_user_role r WHERE project_id = p.id GROUP BY project_id)
	) AS team
FROM
	in_posts p
		INNER JOIN in_postmeta pm
			ON p.ID = pm.post_id
WHERE
	post_type = 'cpm_project'
GROUP BY
	ID
HAVING
	team LIKE '%"48"%' -- все проекты пользователя 48
ORDER BY
	ID ASC
```

> **Прототип SQL.** В реальном коде — параметризованный запрос `$wpdb->prepare()`, имена таблиц `$wpdb->posts` / `$wpdb->postmeta`.

Алгоритм:

1. `get_user_projects($user_id)` проверяет наличие результатов для этого пользователя в своём кэше (использовать **кэш объектов WordPress**). Если найдено — возвращается массив ID проектов, например `[11, 12, 13]`.
2. Если в кэше нет — выполняется подготовка запроса (подстановка `$user_id` в строку `HAVING team LIKE '%"ID"%'` через `$wpdb->prepare()`) и выполнение.
3. Результат преобразуется к массиву найденных ID проектов (строка `team` в результате уже не нужна) и сохраняется в кэш для этого пользователя: `user_id --> [11, 12, 13]`.
4. Возвращается полученный массив ID проектов.

## Кэширование

Кэш прав ACL использует WordPress Object Cache. Сброс — `flush()` (вызывается из `Core_Manager::flush()`). Подробности — `кэширование.md`.
