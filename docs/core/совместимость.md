# Режим совместимости CPM

> **Ключевой принцип: бесшовный переход без скрипта миграции.**
> Отдельный скрипт миграции **не создаётся**. Переход со старой версии CPM на v3 выполняется бесшовно самой архитектурой: **классы умеют читать данные и из старого, и из нового формата, а сохраняют всегда только в новом.** Это означает, что данные обновляются до нового формата постепенно, по мере того как сущности редактируются/сохраняются, — без остановки работы и без массовой одноразовой миграции.

Старая версия CPM хранит данные в кастомных таблицах: проекты, участники и роли, файлы.

Для правильной работы CPM v3 необходим режим обратной совместимости, включаемый константой:

```
CPM_BACKWARD_COMPATIBILITY
```

Константа его определяет, а хук `cpm_settings_backward_compatibility` может его переопределить.

Если режим включён, запросы сущностей читают кастомные таблицы старой версии CPM и восстанавливают данные в новый формат из них. При сохранении сущности данные пишутся уже в новом формате и хранятся только в мета-полях записи.

Режим обратной совместимости сильно усложняет запросы и скрипты и замедляет работу, поэтому должен быть со временем выключен.

## Модель чтения: всегда и старый, и новый формат

Чтение не зависит от того, включён ли «режим» жёстко. Ключевой принцип:

- **При чтении** SQL-запросы всегда запрашивают данные и из нового, и из старого формата. Приоритет отдаётся новому: если у сущности есть данные в обоих форматах, используется только новый. Это реализуется `COALESCE()` в запросах выборки (см. `чтение-участников-sql.md`).
- **При сохранении** данные всегда записываются только в новый формат (мета-поля записи). Старый формат никогда не обновляется.

## Бесшовный переход: как он работает

1. Старые данные (таблица `in_cpm_user_role`, ключи `_assigned` у задач и т.п.) продолжают читаться, пока проект/сущность не будет изменён.
2. Как только сущность сохраняется (любое редактирование), её данные записываются в новый формат. После этого при чтении приоритет нового формата отдаёт только новые данные.
3. Со временем, по мере редактирования, всё больше сущностей переходят в новый формат. Константа `CPM_BACKWARD_COMPATIBILITY` может быть выключена, когда обратная совместимость больше не нужна.

### Преимущества

- **Нет простоя**: миграция не требует остановки работы и не выполняется одним тяжёлым скриптом.
- **Нет риска потери данных**: данные не копируются и не переносятся массово, а перезаписываются штатно при сохранении.
- **Постепенность**: каждая сущность мигрирует индивидуально, при первой же правке.

### Недостатки и нюансы

- **Старые данные сохраняются дольше**: пока сущность не отредактирована, она хранит данные в старом формате. Это допустимо, пока работает чтение обоих форматов.
- **Усложнение SQL-запросов**: подзапросы в `in_cpm_user_role` и `COALESCE()` добавляют накладные расходы на чтение. Это цена обратной совместимости.
- **Необходимость полного покрытия**: каждый тип данных (участники, атрибуты задачи, вложения) должен иметь чтение обоих форматов, иначе бесшовность нарушится.

## Включение/выключение режима

- `CPM_BACKWARD_COMPATIBILITY = true` — включать чтение старых форматов (дефолт при наличии старых данных).
- После полного перехода на новый формат константа выключается, и запросы перестают учитывать старые таблицы/ключи (быстрее и проще).

> Авто-миграция (массовый скрипт чтения всех данных и сохранения в новом формате) ранее планировалась, но **не требуется**: бесшовный переход достигается описанной моделью чтения/записи. Авто-миграция может рассматриваться лишь как необязательная оптимизация для ускорения перехода, но не является требованием.
