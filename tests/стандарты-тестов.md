# Стандарты тестов

Конвенции написания тестов CPM v3.

## Расположение и имена файлов

- Юнит: `tests/unit/<Класс>_Test.php` → класс `<Класс>_Test extends \PHPUnit\Framework\TestCase`.
- Интеграционные: `tests/integration/<Класс>_Test.php` → класс `<Класс>_Test extends \WP_UnitTestCase`.
- Имя файла совпадает с тестируемым классом: `Task_Test.php` тестирует `Task`.
- Тесты на один класс лежат в одном файле; сквозные сценарии (хуки, права, обратная совместимость) — в отдельном файле рядом, например `rights_table_Test.php`.

## Именование методов

- Формат: `test_<поведение>_<условие>` или `@test`-аннотация со свободным именем. Предпочтителен стиль без `@test` — виден в отчётах:
  - `test_save_calls_wp_insert_post_when_id_empty`
  - `test_get_role_returns_administrator_for_admin`
  - `test_can_modify_false_for_foreign_author`
- Один метод = один сценарий. Внутри сценария использовать Arrange → Act → Assert (комментариями или пустыми строками).

## Паттерны WP_Mock (юнит-уровень)

- Замена глобальной функции: `WP_Mock::userFunction('wp_insert_post', ...)`.
  - Обязательно указывать ожидания: `->times(1)`, `->with(...)`, `->andReturn(123)`.
  - По умолчанию WP_Mock строгий: незамоканный вызов глобальной WP-функции — ошибка. Это защита от «тихих» непокрытых путей.
- Мок без проверки аргументов, если они не важны: `WP_Mock::userFunction('get_current_user_id')->andReturn(1)`.
- Глобальные переменные (`$wpdb`): объявлять и подменять в тесте, восстанавливать в `tearDown()`.
- `\WP_Mock::bootstrap()` уже выполнен в `tests/bootstrap.php`; в тестах достаточно `use WP_Mock\Functions;` (при необходимости) и обычных вызовов.
- `tearDown()`: `WP_Mock::tearDown()` вызывается автоматически? — **нет**, для юнит-тестов на PHPUnit 9 с WP_Mock вызывать вручную не требуется только при использовании `WP_MockeryAdapter`; уточнить при настройке. Безопасный паттерн — в `tearDown()` выполнить `\Mockery::close()` при использовании Mockery напрямую.

> Совместимость и точный API WP_Mock зависят от версии PHPUnit/PHP на стенде. Первая настройка фиксирует реальные паттерны в этом файле (раздел «Проверено на стенде»).

## Проверки прав (специфичное)

- Права — критичная зона: помимо «позитивных» тестов (разрешено) писать «негативные» (запрещено) для каждой пары «роль × действие» из `docs/core/права-и-роли.md`.
- Для декораторов обязательно тестировать, что запрещённая операция **не** вызывает `save()`/`delete()`/изменение свойств и выбрасывает `AccessDeniedException`.

## Интеграционные тесты

- Наследуют `WP_UnitTestCase`; фикстуры — через фабрики (`tests/integration/factories/`), см. `фикстуры.md`.
- Не полагаться на порядок тестов; каждый тест самодостаточен.
- Проверку числа SQL-запросов делать через счётчик запросов WP test suite (например, через фильтр `query`/`queries`) для тестов «один запрос на выборку списка».
- Только тестовая БД `cpm_test` (см. `конфигурация.md`).

## Что обязательно в каждом тестовом файле

1. Документация-заголовок: какой класс/сценарий покрывает и на какие пункты матрицы `покрытие.md` ссылается.
2. Раздел «проверено на стенде» для версий/паттернов, если они менялись.

## Приемка

- `vendor/bin/phpunit` (юнит) и интеграционный конфиг выполняются без ошибок и с ожидаемым числом пройденных тестов.
- Новый код не снижает покрытия ключевых зон (права, обратная совместимость, SQL-выборка) — оценивается по матрице, а не только по проценту.
