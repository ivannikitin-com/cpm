# Матрица покрытия

Что и где тестировать для каждого класса ядра. Маркеры: **[U]** — юнит (WP_Mock), **[I]** — интеграционный (реальная БД). Каждый класс из `docs/core/` должен иметь тесты из этого списка; при реализации класса агент обязан добавить соответствующие тесты.

## Общие классы

| Класс | Спецификация | Юнит [U] | Интеграция [I] |
| ----- | ------------ | -------- | -------------- |
| `Plugin` | `docs/02-plugin.md` | Синглтон `get_instance()`; `init()` создаёт менеджеров по хуку `init`; `log()` не пишет при `WP_DEBUG=false` и пишет при `true` | Плагин загружается без ошибок; CPT регистрируются |
| `Base_Manager` | `docs/03-base-manager.md` | Базовые поведение (по мере появления реализации) | — |

## Core_Manager и ACL

| Класс | Юнит [U] | Интеграция [I] |
| ----- | -------- | -------------- |
| `Core_Manager` | Маппинг `$entity_types` по каждому типу; `load_list()` подставляет SQL класса и фильтры через `$wpdb->prepare()`; **пагинация**: `page`/`per_page`/`offset` → `LIMIT`/`OFFSET`; **сортировка**: `orderby`/`order` только по белому списку колонок типа (неизвестный orderby игнорируется); `count_list()`: счётчик по SQL-обёртке (get_var) и через `query_count` для comment/activity; `create()` вызывает `save()` и `flush()`; выбор декоратора по таблице прав (роль × тип) | `load_list()` возвращает массив объектов нужного класса, 1 SQL-запрос на тип; единичный `id` возвращает массив из 1 элемента; пусто → пустой массив; `count_list()` возвращает общее число с пагинацией и без |
| `ACL` | Значения констант; `get_role()`: admin → `ADMINISTRATOR` без дальнейших действий; сущность без проекта → `NO_ROLE`; участник → его роль; не-участник → `NO_ROLE`; `get_user_projects()`: кэш (object cache) и запрос `$wpdb`; `flush()` сбрасывает кэш | `get_user_projects()` на реальных данных: приоритет `_team` над `in_cpm_user_role` (COALESCE); `[id1, id2]` |

## Team и User

| Класс | Юнит [U] | Интеграция [I] |
| ----- | -------- | -------------- |
| `Team` | Конструктор парсит строку `"12":manager,"15":co_worker`; `add()`/`remove()`; `get_members()` возвращает каноничную строку; пустой members; кавычки в `user_id` (12 не путается с 112) | Сохранение `_team` в БД и чтение обратно (round-trip) |
| `User` | Конструктор не вызывает `load()`; `get_name()`/`get_avatar()` лениво грузят; `load()` не найден → `BadUserException` | — (чтение реального `WP_User`) |

## Сущности — базовые

| Класс | Юнит [U] | Интеграция [I] |
| ----- | -------- | -------------- |
| `Entity` | `get_type()` убирает namespace и нижний регистр (в т.ч. у обёрнутых декоратором объектов); `get_wp_args()` — структура массива (мета `_team`, `_thumbnail_id`); `save()`: insert (id=0) вызывает `wp_insert_post` и присваивает id, update вызывает `wp_update_post`; после `save()` вызывается `flush()`; `delete()` рекурсивно удаляет детей с `$is_recursion=true` и вызывает `delete_entity()`; `flush()` откладывается при `$is_recursion`; хуки create/update/delete вызываются в правильном порядке (типизированный → общий); delete-хук только на корне рекурсии; `delete_entity()` → `wp_delete_post(..., CPM_FORCE_DELETE)`; `get_thumbnail()` по цепочке родительства | Сохранение сущности создаёт запись с правильным CPT и мета; повторное сохранение обновляет; удаление удаляет запись |
| `Project_Entity` | `get_project()` создаёт `Project` по `project_id` (мокаем фабрику/кэш); свойства `project_id`/`project_title`/`project_slug` заполняются | — |

| ----- | -------- | -------------- |

| `Task` | `get_wp_args()` (мета `_start/_due/_completed/_completed_on/_completed_by/_task_privacy`); `get_project()` при `parent` = список/проект/задача | SQL: чтение team из `_assigned` (несколько записей postmeta) → формат team; иерархия: parent=список (основной), parent=проект, parent=задача; CPT `cpm_task` |
| `Message` | `get_wp_args()` (мета `_message_privacy/_milestone`) | SQL: privacy/milestone, parent=проект; CPT `cpm_message` |
| `Milestone` | `get_wp_args()` (мета `_due/_completed`) | SQL: due/completed; CPT `cpm_milestone` |
| `Note` | `get_wp_args()` (мета `_doc_type`) | SQL: doc_type, parent=проект; **CPT `cpm_docs`** |
| `Comment` | `save()`/`get_wp_args()`/`delete_entity()` под `comments`; `get_project()` по цепочке; чтение: `query_rows()` с пагинацией (`per_page`/`page`/`offset`) и сортировкой (маппинг `orderby` → поле WP), `query_count()` | Хранение через `wp_insert_comment`; чтение через `get_comments`; `commentmeta._files`; привязка к сущностям разных типов; `get_project()` по цепочке |
| `Attachment` | `get_project()` через `_project`; методы URL/иконок; **загрузка**: `validate_upload()` (нет файла/ошибка/размер/тип по whitelist), `create_from_upload()` (move в `uploads/cpm`, `wp_insert_attachment`, мета `_project`/`_parent`) | Чтение старых вложений (мета `_project`, `_wp_attached_file`); связь с комментарием через `commentmeta._files`; загрузка реального файла |
| `Activity` | Формирование текста сообщения; подписка на хуки create/update/delete (лог всех мутаций сущностей проекта, кроме activity и без проекта); чтение: `query_rows()` с пагинацией/сортировкой, `query_count()`; `save()` только для чтения | Чтение лога: `comment_type='cpm_activity'`; `load_list('activity', ...)` по `project_id`/`id`/`parent` (SQL из `docs/core/activity.md`); фильтр по участнику/администратору; старые записи выводятся как есть |

## Сквозные сценарии

| Сценарий | Уровень |
| -------- | ------- |
| **Таблица прав**: для каждой пары «роль × тип сущности» из `docs/core/права-и-роли.md` выбор декоратора в `Core_Manager` даёт ожидаемый декоратор | [U] |
| **Обратная совместимость**: проект с `_team` (новый) и записями в `in_cpm_user_role` (старый) читается только по новому; проект только со старыми — по старому | [I] |
| **Хуки**: `cpm_core_entity_create_{type}` + `create`, `update_{type}` + `update`, `delete_{type}` + `delete`; delete-хук не срабатывает на вложенных шагах рекурсии | [U] + [I] |
| **Права на выборке**: администратор видит все сущности (фильтр `is_admin` не применяется); участник — только своих проектов; не-участник — ничего | [I] |
| **Кэш**: `flush()` вызывается после save/create/delete (не в рекурсии); `ACL::flush()` из `Core_Manager::flush()` | [U] |

## Правило соответствия

- Тест считается принятым, если он покрывает пункты матрицы для этого класса. Пункт матрицы без теста при сдаче класса — дефект спецификации тестирования.
- Изменение спецификации в `docs/core/` влечёт обновление матрицы и соответствующих тестов в том же PR/изменении.
